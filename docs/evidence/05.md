# Evidence — milestone 05 scripts

Status: **local component and real-process integration gates passed**. Garage
was exercised as an actual S3 backend in the local integration environment.
No milestone 05 deployment to the physical Balena robot or hosted production
storage has been performed; those are not claimed by these results.

## Garage compatibility preflight — 2026-11-12

```bash
bash tests/e2e/05-garage.sh
```

Passed against a disposable local single-node Garage 2.5.0 container, image
`sha256:677e5b758e4425a325b811c425c026bf35a4bf42f7ddbaa773de3f4fd779a5a5`;
the client used boto3 1.40.61 and botocore 1.40.76. It performed authenticated
S3 PUT/GET, verified the downloaded bytes, wrote those bytes to a separate key,
overwrote the incoming key, and verified the promoted object and a presigned
GET remained unchanged. Both objects and the disposable container were removed.
Keys and the RPC secret were generated for this run and not recorded here.
The same script also ran `tests/integration/garage-probe` in the .NET 10 SDK
container, using the actual API `S3ObjectStore` with AWSSDK.S3 4.0.104.12 to
put, get and delete an object. This found that Garage rejected the SDK's default
chunked payload encoding; setting `UseChunkEncoding = false` made the real
adapter round trip pass with payload signing retained. See the integrated
Garage run below for the Ringfour upload and execution path.

## Integrated local acceptance — 2026-11-12

Prerequisites: `.auth.env`, a live Auth0 CLI login, Docker and uv, with ports
18085–18087 free. From the repository root:

```bash
bash tests/e2e/05-scripts.sh
RINGFOUR_TEST_STORAGE=garage bash tests/e2e/05-scripts.sh
```

Both runs passed with real CLI, API, PostgreSQL, daemon, Runner and process
execution. The second run used Garage 2.5.0 as the API's S3 store; the first
used its filesystem store. The main execution used the real Auth0 access token.
A second local API process with an ephemeral test-only signing key and a
different subject/organization verified cross-organization reads return 404;
that check is not a second live Auth0 account.

Observed in both storage configurations: the milestone 04 diagnostic fixture
still ran successfully; interrupted upload could not be
finalized and a full retry succeeded; hello produced stdout, stderr, exit 0 and
verified downloadable artifact bytes with an actor; repeating the same key
returned the same execution; a failing process returned exit 7; a hash-pinned
`six==1.17.0` lock installed and an incorrect hash failed preparation; stop
cancelled a running script; daemon and API restarts during output transfer
preserved all output without gaps or duplicates; and Runner restart marked the
interrupted process `interrupted_unknown_outcome`. The Garage variant also
stopped Garage, observed 503 for an upload, restarted it and successfully
retried. Each test created and removed its own containers, network and volumes;
the existing local database, robot and Balena device were not changed.

Environment: Docker client 29.9.2 / server 28.3.3, Compose 5.5.1,
.NET SDK 10.0.403, PostgreSQL image 18, Python 3.13, uv 0.12.1,
Node 26.13.0, AWSSDK.S3 4.0.104.12, Garage 2.5.0. Per-environment Python
dependency disk usage relies on deployment quotas; Ringfour does not currently
enforce a hard venv byte quota. Human procedures and retention limits are in
`docs/human-testing/05.md`.
