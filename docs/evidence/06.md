## Follow-up: base101 local Agent socket — 2026-11-12

`~/Work/robots/base101/docker-compose.balena.yml` now connects Runner to the
Agent at `unix:///run/robocore/agent.sock` using a dedicated named socket
volume. The Agent image creates that directory owned by UID 1000; Runner mounts
the volume read-only and both processes have matching UID 1000. The Agent's TCP
listener remains enabled for robot-local observer clients, bound to
`127.0.0.1:10101`, and no longer listens on the robot's LAN interfaces. Existing
Agent state and map volumes are unchanged. The socket is mode 0600 and the
Agent treats matching UID local peers as trusted operators; a read-only volume
mount does not make Agent commands read-only. The mission used here only reads.

```bash
docker compose -f ~/Work/robots/base101/docker-compose.balena.yml config --quiet
docker build -f ~/Work/robots/base101/docker/Dockerfile.agent -t base101-agent:socket-test ~/Work/robots/base101
ROBOCORE_TEST_SOCKET=1 bash tests/e2e/06-sdk-example.sh
```

The Compose check and isolated SDK/Runner/Agent test passed. The test used the
actual modified Agent Dockerfile, a fresh dedicated socket volume, the Runner
image and the SDK capabilities mission; it killed and restarted Agent before
running the mission to verify socket recovery. A synthetic profile and Fast DDS
were used because the local test has no robot Zenoh router. The first attempt
with the robot's normal Zenoh configuration could not start without that router;
no physical ROS result is claimed. The Balena configuration has not yet been
rebuilt or deployed on the device. Existing robot-side uncommitted changes were
preserved and no robot-side commit was created.


## Follow-up: live sensor diagnostics — 2026-11-12

Added the user-owned `../missions/diagnostics` mission. It uses the pinned SDK's
async `Robot.connect`, `ping`, `imu` and per-camera `stream` APIs. The Unix
socket connection explicitly selects SDK network payload transport because the
Runner and Agent do not share `/dev/shm`. Every two seconds it reports ping,
unique IMU timestamps observed at a maximum 10 Hz poll rate, latest recent
acceleration/gyro, and camera frames delivered at a requested maximum 5 fps.
These are capped client-observed rates, not the sensors' native ROS topic rates.
Missing data is reported; the mission runs until explicitly stopped. It does not
issue motion commands or create camera artifacts.

```bash
bash tests/e2e/06-diagnostics.sh
ROBOCORE_TEST_NO_SENSORS=1 bash tests/e2e/06-diagnostics.sh
```

Both passed with the actual Runner, pinned SDK, actual Agent image and Unix
socket. The first used a synthetic profile and synthetic ROS IMU/image publishers
(Fast DDS) and observed nonzero IMU and camera rates; the second omitted
publishers and showed unavailable/waiting while ping continued. Both verified
that stopping cancels the mission and cleaned up isolated resources. No physical
robot sensor reading or deployed 06 diagnostics result is claimed here.

## Follow-up: user-reported base101 diagnostics — 2026-11-12

The user supplied diagnostics output from base101 showing ping, IMU values and
camera frame delivery. On 2026-11-12 at approximately 23:24 EET, a read-only
Platform API inspection found deployment `3e186652-bd82-47b4-912d-bf097e0438d1`
assigned to base101 and execution `08d35b1d-5d12-44f4-bdc4-22ff316f83f7`
still running. The hosted execution's stored stdout contained 470 complete
matching samples: ping median 8.8 ms (range 1.1–110.1 ms), observed unique IMU
mean 8.04 Hz, and camera delivery mean 4.97 fps. These are the first captured
samples, not necessarily the latest: stdout had reached its 65,536-byte cap
and `truncated` was true. The mission requests camera streams at 5 fps and
sleeps 100 ms after each IMU read; these results therefore do not measure the
native ROS sensor rates. Counts in individual short reporting windows can
exceed the requested average by one frame. The repository's robot profile
requests up to 30 camera fps, but the active robot configuration and native
sensor throughput were not independently measured in this inspection.

No process was stopped or deployed during the investigation. The user's
reported output and the hosted execution record are evidence of observed SDK
sensor data, not a direct ROS topic-rate benchmark or a completed milestone 10
hardware acceptance.
