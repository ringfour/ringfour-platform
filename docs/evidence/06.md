## Follow-up: live sensor diagnostics — 2026-11-12

Added the user-owned `../missions/diagnostics` mission. It uses the pinned SDK's
async `Robot.connect`, `ping`, `imu` and per-camera `stream` APIs. The Unix
socket connection explicitly selects SDK network payload transport because the
Runner and Agent do not share `/dev/shm`. Every two seconds it reports ping,
unique IMU timestamps observed at a maximum 10 Hz poll rate, latest recent

Missing data is reported; the mission runs until explicitly stopped. It does not

requests up to 30 camera fps, but the active robot configuration and native
sensor throughput were not independently measured in this inspection.

No process was stopped or deployed during the investigation. The user's
reported output and the hosted execution record are evidence of observed SDK
sensor data, not a direct ROS topic-rate benchmark or a completed milestone 10

## CLI mission context and onboarding — 2026-11-13

The CLI writes visible `ringfour.context.json` after a successful push and
excludes it from bundles. Context-based commands verify the current deployment
and latest execution with the API. They reject pending or changed revisions
and ambiguous robot selection. A missing context can be recovered from an
unambiguous organization mission and deployment. API URLs containing embedded
credentials, query parameters or fragments are rejected before saving context.
`push --start --follow` explicitly waits for preparation, starts the selected
revision, and follows output. See the human-testing guide and CLI README for
commands and limitations. Application-level onboarding READMEs were added.

A local integration rerun revealed that a completed execution from the previous
revision could overwrite the observed state of a newly prepared revision. The
API projection was changed to apply execution status only to its selected
revision; it also leaves a freshly completed preparation authoritative when
the same revision was prepared again.
