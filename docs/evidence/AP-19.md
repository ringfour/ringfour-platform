# AP-19 evidence — responsive App state

## API/Daemon benchmark · 25 November 2026

This backend-only benchmark supplements the earlier single-run and UI
investigation below. It measures the durable dispatch path before and after
adding commit-triggered API notifications and daemon wakeups. The PostgreSQL
operation journal remains authoritative; periodic sweeps remain the recovery
path. No UI timings are included in this comparison.

| Segment (20 start/stop samples) | Before p95 | After p95 |
|---|---:|---:|
| Start HTTP response | 23.7 ms | 21.4 ms |
| Start command dispatch acknowledgement | 1802.2 ms | 44.8 ms |
| Start acknowledgement → engine start | 1739.6 ms | 1343.7 ms |
| Start request → device-observed running | 3596.8 ms | 1558.1 ms |
| Stop HTTP response | 11.4 ms | 11.5 ms |
| Stop command dispatch acknowledgement | 1992.2 ms | 22.3 ms |
| Stop acknowledgement → engine end | 524.6 ms | 79.7 ms |
| Stop request → device-observed terminal | 2262.7 ms | 263.6 ms |

The observed stop p95 improved 8.6× and start dispatch acknowledgement 40.2×.
Observed start is 2.3× faster but remains just above the 1.5 s target in this
fixture. The nested Docker-in-Docker engine uses vfs storage: container create
was 1203 ms p95 after the change (763.8 ms median, with a 2439.6 ms outlier).
That is a measured fixture segment, not evidence about the host's live Docker
Engine. Do not attribute the remaining start time to PostgreSQL: the benchmark
also recorded SQL summaries, while dispatch was the segment materially reduced
by this change.

At 100 catalog Apps, API read p95s were 3.0–6.9 ms across robots, imports,
active/recent runs, installations, logbook, settings and files; eight-way
concurrent active-run reads were 6.6 ms p95. Live authenticated API reads on
the operator stack were 3.0–5.0 ms p95 for the same projection family.
`/v1/me` was 202.7 ms p95 because it performs Auth0 `/userinfo`; token setup was
excluded. This call does not explain multi-second App lifecycle waits.

### Post-reload live check

After the operator reloaded both stacks, read-only API sampling again measured
projection p95s of 2.6–5.7 ms across 100 samples per endpoint. `/v1/me` was
220 ms p95 (10 samples, including Auth0 `/userinfo`). A single real virt2
start/stop cycle then confirmed the new dispatch wakeups are active: command
acknowledgement was 34 ms for start and 19 ms for stop; device-observed start
was 565 ms and terminal stop 979 ms. This is one live sample, not a percentile
claim. The operator had the Console open during the cycle and confirmed that
the UI state updated live in place. The App ended with exit code 1 after the stop because the pinned
Robot Check example tried to publish `summary.json` using a path outside
`RINGFOUR_ARTIFACT_DIR`; the start and stop operations themselves succeeded.
See the AP-17 note for that example issue. The AP-19 timings isolate responsive
dispatch and observation; they do not certify artifact publication.

The fixture covers one robot, up to 100 catalog Apps and 20 lifecycle samples;
it does not satisfy the separate ten-robot loaded UI target. The live API
evidence is read-only. The source code containing wakeups is not yet loaded in
the running API/virtual Daemon because the workspace rule reserves stack
reloads for the operator. Rerun the after benchmark and live start/stop check
after the operator reloads those services.

Reproduction from the repository root (the scripts create disposable test
services and clean them up):

```bash
uv run --project apps/daemon python -u tests/e2e/ap17-settings.py --benchmark-only \
  --backend-report docs/evidence/ap19-backend-before.json --samples 20
uv run --project apps/daemon python -u tests/e2e/ap17-settings.py \
  --evidence-report docs/evidence/ap17-process.json \
  --backend-report docs/evidence/ap19-backend-after.json --samples 20
uv run --project apps/cli python tests/e2e/ap19-live-reads.py \
  --output docs/evidence/ap19-live-api-before.json
```

The first command was run against pre-wakeup source; the second uses current
source. API and Daemon recovery fallback intervals are held constant between
the two backend runs.

**Status · 25 November 2026:** investigation confirms Docker was the wait
surface for one severe shutdown delay, but the measured cause was lock
contention in the App Daemon. The Daemon waited for Docker's 10-second graceful
stop while holding a lock the App needed to upload its final summary. Releasing
that lock in both stop call layers reduced a live Camera Snapshot Loop stop
from 11.48 seconds to 0.833 seconds and the App exited cleanly with its summary
artifact. Ordinary sampled Docker API calls are in the 4–44 ms range. This does
not yet explain all reported 3–5 second view updates: full browser-to-API-
to-database-to-render traces and the agreed loaded fixture remain outstanding.

## Findings and changes

- The Docker stop endpoint waits up to `t=10` for graceful process exit. The
  old 11.5-second stop was not slow general Docker request handling: the App
  handled SIGTERM, then called the Daemon to publish its final artifact while
  the daemon's executor mutex was held across Docker's wait. The operation
  handler also held the same reentrant mutex around that call. The App could
  not finish until Docker killed it.
- Both Daemon lock scopes now release their mutex before waiting on Docker.
  Live run `4951fdbf-0e6f-4ef1-825f-0e7fdda23071` stopped with exit code 0 and
  uploaded its summary. The virtual Apps topology was rebuilt/restarted to
  load the fix; the Platform API and database volumes were not recreated.
- The Apps Console constructed an invalid query string for recent runs by
  appending a second `?` before `limit=50`. `withQuery()` now appends `&` when
  a query already exists; a regression verifies both bounded run requests.
- App operation status polling stopped at terminal state without telling its
  owning view to reload. `AppOperationStatus` now invokes an optional,
  once-per-operation terminal callback. Apps and Robot detail use it to refresh
  their projections without clearing the current view. The Console was
  rebuilt/recreated with this fix. A unit regression verifies exactly one
  callback.
- App detail section tabs were also ordinary `<a>` navigations. That caused a
  full page reload on Overview → Settings, reinitializing the Console and
  workspace data before showing the selected section. Tab clicks now use the
  existing history-based client navigation while retaining normal modified
  clicks (for example, Ctrl/Cmd-click to open another tab). The Console was
  rebuilt/recreated; its HTTP endpoint is healthy. This should remove the
  reload delay, while Settings data still loads asynchronously inside the
  already-visible section.
- `/v1/me` calls Auth0 `/userinfo` each time; measured p95 is about 193 ms.
  This is a concrete avoidable round trip, but not a sufficient explanation
  for the entire reported delay.
- Camera Snapshot Loop is stopped. Latest relevant Docker containers are
  `Exited (0)`; no App run was left active at the time of this check.

## Whole-frontend follow-up · 25 November 2026

During AP-21's `uifix.md` pass the owner reported whole-frontend slowness and
explicitly authorized restarts. Live API logs showed common App/robot reads at
roughly 2–3ms median, with `/v1/me` at 212ms median. The Home/Robots loader waited
on profile/member attribution and undisplayed artifact counts; those unused
reads are removed. Timeline opts into attribution explicitly. The local Console
also ran Vite/React development mode. Only Console was rebuilt/recreated as the
existing production Nginx target, with compression and the same host port 5173.

Five warm browser-fixture samples per action measured Home→Robots p50 350→150ms
and Robots→Home 349.8→149.9ms, with zero document reloads. Fixtures use 5ms reads
and a 220ms profile delay; they are not authenticated production percentiles.
The deployed runtime serves ~202kB gzipped compiled JavaScript and passes real
sign-in/proxy/deep-link/401 checks. Full details, image identity, JSON evidence
and reproducible commands are in [AP-21 evidence](AP-21.md). The logged-in
browser/load matrix still needs human confirmation; these measurements do not
reopen or replace the earlier API/Daemon benchmarks.
