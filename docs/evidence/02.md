## Integrated acceptance (real Auth0, real processes)

`tests/e2e/02-enrollment.sh` — PASS (run 2026-11-10, repeatable; it resets
the daemon volume first):

1. `/v1/device/enroll` and `/v1/device/authenticate` reject garbage with 401
   `invalid_token` **without any human token** (unauthenticated by design).
2. Owner (account 1, CLI login) creates org + robot; robot starts unenrolled.
3. `ringfour-cli robot enrollment-token` issues a single-use token;
   `ringfour-cli daemon enroll <token>` drives the local daemon, which calls
   `POST /v1/device/enroll`, stores the secret at `/data/robot-credential`
   (0600) and commits the SQLite `device_identity` singleton.
4. `docker compose restart daemon` → `ringfour-cli daemon identity` still reports
   the same robot/organization/credential ids (restart recovery).
5. Reusing the consumed token at the platform → 401 `invalid_token`.
6. Rotation: old secret (read from the daemon volume, never printed) still
   authenticates during the overlap; the new secret authenticates too.
7. Revoking the old credential → its authenticate immediately 401s with
   `invalid_token`; the new credential keeps working.
8. Live DB spot-check: `robot_audit_events` holds all five event types with
   `enrolled` rows actor-less; all `token_hash`/`secret_hash` values are
   64-char SHA-256 hex — no plaintext secrets anywhere.

## Decisions and deviations

- **New endpoint `POST /v1/device/authenticate`** (new design, not in the
  starter contracts): credential verification is needed in 02 to prove
  revocation/expiry rejection; 03's real device flows will build on it.
  Identity is always derived from the verified credential, never from
  caller-supplied claims.
- **Role matrix**: robot administration (create, token issuance, rotate,
  revoke) is owner-only; list/read is any member. Rationale: device
  administration is an owner responsibility in v0.1; relaxing later is
  backwards-compatible.
- **Secret formats**: enrollment tokens `rft_<43 urlsafe>` and credential
  secrets `rfs_<43 urlsafe>` (32 random bytes); only SHA-256 hex hashes are
  stored. Token TTL 15 min (`Enrollment:TokenTtlMinutes`), rotation overlap
  300 s (`Enrollment:RotationOverlapSeconds`).
- **Atomic consumption**: one conditional
  `UPDATE enrollment_tokens SET consumed_at=now() WHERE … AND consumed_at IS
  NULL AND expires_at > now() RETURNING …` inside the transaction that also
  creates the credential, stamps `enrolled_at` and writes the audit event.
  Losers match no rows → 401.
- **Daemon commit order**: the secret file is written (0600, atomic
  replace) before the `device_identity` row is committed; on boot a committed
  identity without its secret logs an error and surfaces
  `error: credential_missing` on `GET /v1/identity`. Readiness is unaffected
  (per 00, readiness reports dependency health only).
- **Lost enroll responses**: not recoverable client-side by design; the
  contract documents that an owner issues a fresh token (the stranded
  credential can be revoked).
- **No audit endpoint in 02**: `robot_audit_events` is verified via direct
  DB assertions; exposing it is left to a later milestone.
- **Console robot inspector**: delivered (Robots view: org picker, robot
  list with enrollment badges, create form, detail panel with one-time
  token/secret display, credential list with rotate/revoke; read-only for
  non-owner members). 12/12 vitest.
- **Idempotency-Key**: still deferred to 03 (same as 01).

### Balena configuration diagnosis — 2026-11-12

Read-only inspection of the robot's deployed daemon found the pairing/status
modules present, but `PLATFORM_API_URL` unset, causing the default
`http://localhost:8080` to be used inside the container. The robot container
could reach the local development API on the Mac's LAN address and got HTTP
200 from `/health/ready`. Its saved pairing request had never been registered.
The daemon had no `RUNNER_AUTH_TOKEN`; Runner readiness reported volume and
uv OK but authentication failed. The daemon exposed port 8083 in its image but
published only loopback port 8081 in the deployed service. No robot filesystem,
variables, deployment, or physical motion were changed by this inspection.

The daemon now discards a pending pairing request when the Platform URL changes
only if the request was never confirmed by the old Platform. A confirmed pending
request is retained to avoid losing a possible claim. Network failures produce a
concise warning naming the `PLATFORM_API_URL` configuration rather than a full
traceback. `uv run --project apps/daemon pytest apps/daemon/tests -q` passed
42 tests, including URL-correction and confirmed-request preservation. The
updated source had not yet been rebuilt or deployed at that point. During the
subsequent physical smoke, the deployed pairing module matched this checkout.
