## Contract and local durable state — 2026-11-17

The proposed contract now distinguishes hosted `submitted` responses from
daemon-confirmed terminal outcomes. The daemon owns the deadline and persists
execution-bound requests in SQLite. Identical request replay is accepted;
conflicting reuse is rejected. Local reads resolve deadlines, bounded waits do
not fabricate terminal state, and an observed stopped execution cancels a
pending request. Runner injects only an execution-scoped credential into the
mission. The independently packaged Python runtime exposes create/get/wait.

No tests or stack reload were run by the agent in this slice. The user
subsequently rebuilt ringfour-virtual; its daemon and Runner were observed up,
but no interaction acceptance was executed.

## Hosted response handshake and CLI — 2026-11-17

The API now persists organization-scoped interactions and one atomic winning
operator response. A machine-authenticated bidirectional sync stores the
daemon-authoritative state and returns a provisional hosted response. Only the
daemon can turn that response into `answered`; its next sync marks the hosted
response `applied`, `rejected_timed_out` or `rejected_cancelled`. Human response
submission checks organization operator membership, choice membership, hosted
deadline, terminal state and idempotency key under a row lock.

`ringfour-cli hitl list`, `show` and `respond` use these hosted endpoints. The
respond command explicitly reports that API acceptance is not device
confirmation.

The Console Overview now includes a polling operator-request queue. Pending
requests show robot, deadline, prompt and finite choices inline. After a choice
is submitted, actions remain disabled and the card explicitly waits for device
confirmation; the request disappears only after the daemon reports a terminal
state. A stable per-request idempotency key is retained across a lost HTTP
response.

## Indefinite wait by default — 2026-11-17

The default interaction now has no deadline. The SDK `wait()` continues
bounded long polls until the interaction becomes terminal, so an unanswered
request leaves the mission waiting. Callers may opt into a deadline only by
providing both a timezone-aware deadline and a safe `timeout_outcome` choice.
When the daemon reports `timed_out`, `wait(..., on_timeout=callback)` invokes
the callback once with the terminal interaction, then returns that interaction.
This lets mission code log, raise, or take a mission-specific recovery path;
the durable daemon outcome remains authoritative. The Console labels
deadline-free requests “No timeout”.

The change adds nullable deadline/timeout fields to the API and daemon
persistence, pairing constraints in API/JSON Schema validation, and fixtures
for deadline-free create, pending and device-sync documents. Focused tests:
contracts 32 passed; Python runtime 4 passed; daemon interaction/health/logbook
15 passed. Live acceptance is pending a reload of Platform and ringfour-virtual.

## HITL attribution in Logbook — 2026-11-17

The API now writes hosted Logbook records in the same PostgreSQL transaction as
the interaction state change. First synchronization records
`human.interaction.requested` under the verified execution initiator. A
daemon-confirmed answer records `human.interaction.answered` under the actual
operator, with the selected label/value and response ID. Confirmed timeout and
cancellation produce system events with no human actor. Provisional API
submission alone creates no answer event. Hosted entries use a null local
sequence and therefore do not alter the daemon's contiguous device outbox.
