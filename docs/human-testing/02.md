# Human testing guide — milestone 02 (robot enrollment)

For the current onboarding flow, start with **Device-initiated pairing** below:
add a robot directly in the Console using its device code. Sections 1–9 record
the earlier token-based flow, which remains available for compatibility.

Everything a human can use and verify after milestone 02: creating robots,
issuing single-use enrollment tokens, enrolling the local device daemon
through the CLI, restart recovery, credential rotation with overlap, and
revocation.

Milestone 01 functionality (login, organizations, Console) still applies —
see `docs/human-testing/01.md`. Prerequisites are the same: stack running
(`docker compose -f infra/compose/docker-compose.yml up -d --build`), CLI
environment sourced from `.auth.env`, and `ringfour-cli login` approved as
account 1 (the owner).

## 1. Create a robot

```bash
cd apps/cli
set -a; . ../../.auth.env; set +a
export RINGFOUR_AUTH0_DOMAIN="$AUTH0_DOMAIN"
export RINGFOUR_AUTH0_CLIENT_ID="$AUTH0_CLI_CLIENT_ID"
export RINGFOUR_AUTH0_AUDIENCE="$AUTH0_AUDIENCE"

uv run ringfour-cli org list                      # pick or create an org you own
uv run ringfour-cli org select <org-id>
uv run ringfour-cli robot create "warehouse-01"
uv run ringfour-cli robot list                    # robot appears, Enrolled = no
uv run ringfour-cli robot show <robot-id>         # Enrolled: no
```

Expected: `Created robot <robot-id> (warehouse-01)`. Non-owners get
`403 forbidden`; people outside the org get `404 not_found`.

## 2. Issue an enrollment token

```bash
uv run ringfour-cli robot enrollment-token <robot-id>
```

Expected: a token like `rft_…` printed **once**, with its expiry (15 minutes
by default). It is single-use and never retrievable again — if you lose it,
issue another one; unconsumed tokens can simply be left to expire.

## 3. Enroll the device through the local daemon

```bash
uv run ringfour-cli daemon enroll <token>
uv run ringfour-cli daemon identity
```

Expected: `Device enrolled.` with the robot/organization/credential ids, and
the identity view shows the same ids with no error. The daemon stored the
credential secret at `/data/robot-credential` (mode 0600) inside its
container and committed its SQLite `device_identity` row.

Re-running `daemon enroll` now fails: the device is already enrolled.

## 4. Restart recovery

```bash
docker compose -f infra/compose/docker-compose.yml restart daemon
sleep 2
uv run ringfour-cli daemon identity
```

Expected: the same identity, no error — the binding survives restarts.

## 5. Token misuse is rejected

```bash
curl -s -H 'content-type: application/json' \
  -d '{"token":"<the consumed token from step 2>"}' \
  localhost:8080/v1/device/enroll
```

Expected: `401` with `{"error":{"code":"invalid_token", …}}` — consumed
tokens never work again. A garbage token behaves identically, and none of
this needs a human login: the device endpoints are unauthenticated by
design.

## 6. Rotate the credential (overlap)

```bash
uv run ringfour-cli robot credentials <robot-id>    # one credential, no expiry
uv run ringfour-cli robot rotate <robot-id>         # prints new secret ONCE
uv run ringfour-cli robot credentials <robot-id>    # old credential now has expires_at
```

Expected: the previous credential keeps working until its new `expires_at`
(5 minutes by default) so a daemon mid-rotation never loses access. The new
secret is shown exactly once — store it nowhere; the daemon picks up
rotation flows in a later milestone.

## 7. Revoke and prove rejection

```bash
uv run ringfour-cli robot revoke <robot-id> <old-credential-id>
```

Expected: `Revoked credential …`. To prove the old secret is dead, read it
from the daemon volume and try it (do not save it anywhere):

```bash
old_secret=$(docker compose -f infra/compose/docker-compose.yml exec -T daemon cat /data/robot-credential)
old_id=<old-credential-id>
curl -s -H 'content-type: application/json' \
  -d "{\"credential_id\":\"$old_id\",\"secret\":\"$old_secret\"}" \
  localhost:8080/v1/device/authenticate
# {"error":{"code":"invalid_token", …}} — HTTP 401
```

## 8. Cross-account isolation (account 2)

Log in as account 2 (`uv run ringfour-cli login --no-browser`, approve in an
incognito window — see guide 01, step 5), then:

```bash
uv run ringfour-cli robot show <robot-id>           # 404 not_found
uv run ringfour-cli robot enrollment-token <robot-id>  # 404 not_found
```

Expected: account 2 learns nothing about account 1's robots — 404, never 403,
because it is not a member of the org. Restore account 1 afterwards
(`uv run ringfour-cli login`).

## 9. Console robot inspector

```bash
open http://localhost:5173
```

- Sign in, then open the **Robots** view in the nav.
- Pick an organization from the picker; the robot list shows enrollment
  status badges (`enrolled` / `not enrolled`).
- As an **owner** you get the create form; create a robot, click its name to
  open the detail panel, and use **Issue enrollment token** — the token is
  displayed once in a highlighted box (pass it to `ringfour-cli daemon enroll`),
  and **Dismiss** removes it from the screen permanently.
- **Rotate credential** shows the new secret once; the credentials table
  lists state badges and offers **Revoke** for active credentials.
- As a **non-owner member** (add account 2 as a developer to your org to try
  this), the same views render read-only: no create form, no token/rotate/
  revoke buttons.

## Troubleshooting

| Symptom | Cause / fix |
|---|---|
| `daemon enroll` says "Daemon unreachable" | Daemon container not running: `docker compose -f infra/compose/docker-compose.yml up -d daemon`. |
| `Enrollment failed: enrollment token rejected by the platform` | Token expired (15 min TTL) or already consumed — issue a fresh one. |
| `daemon identity` shows `Error: credential_missing` | The secret file in the daemon volume was deleted; re-enroll a fresh robot (wipe with `docker compose … down -v` or the e2e script's reset). |
| `403 forbidden` on `robot create` / `enrollment-token` / `rotate` / `revoke` | You are a member but not an owner of the org — robot administration is owner-only. |
| `404 not_found` as the org owner | Wrong `--org` / selection: `ringfour-cli org list` and `org select` the right one. |

## Device-initiated pairing (recommended flow)

With the updated API and daemon images, an unenrolled daemon creates a pairing
request automatically. Open `http://<robot-lan-ip>:8083/` on the same trusted
network. The separate read-only page shows a pairing code and expiry; the daemon
also prints the code in its logs. It refreshes automatically. Anyone able to see
this page can read the current code, so limit network access to trusted operators.
The page has no enrollment or device-control endpoints.

Sign in to the Console as an organization owner and open **Robots**. Select the
organization, then under **Add a robot** enter the pairing code and a name.
Choose **Add robot**; the record is created as part of pairing. If the robot
already exists as an unpaired record, choose it under **Pair with** instead.

The daemon
receives its identity automatically; the page changes to `Enrolled · connected`
or `Enrolled · reconnecting`. The platform code expires after 10 minutes and a
new code appears automatically; a code can be claimed once. On restart before
claim, the daemon reuses the still-valid pending request. Restart after claim
keeps the enrolled identity. If the daemon cannot reach the API, the page says
`Waiting for platform`; check the daemon's `PLATFORM_API_URL` and connectivity.
An already enrolled daemon does not generate a new code.

For Balena, publish the daemon status port `8083:8083`, retain its data volume,
and configure `PLATFORM_API_URL` plus the shared Runner secret as described in
`infra/balena/README.md`. Port 8083 is only the read-only status app; the daemon
control API remains on port 8081. The current physical robot image must be
updated before it can show this page. Keep the original token-driven flow above
for compatibility and recovery.

If the daemon was started with a missing or wrong Platform URL and never
registered the request, the updated daemon automatically discards that
unregistered request after `PLATFORM_API_URL` is corrected and starts a new one.
A request already confirmed by another Platform is retained to avoid losing a
claim; restore that Platform URL or follow a deliberate recovery procedure.
If Runner readiness reports `auth: fail`, set the same `RUNNER_AUTH_TOKEN` on
both services through Balena's runtime variables.
