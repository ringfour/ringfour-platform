# AP-13 two-user, two-workspace, two-robot acceptance

This is the end-to-end acceptance guide for the Apps workflow. It uses the
existing `cdr` WSL account as publisher and the `ring1` WSL account, signed in
with its Outlook-backed Auth0 identity, as consumer. Each account has its own
CLI tool environment, keyring and workspace. The acceptance uses two numbered
App-capable virtual robots on one Docker Engine and the local registry.

This guide never asks users to share Auth0 tokens, CLI keyrings, enrollment
tokens after enrollment, or App runtime credentials. Write down the public user,
organization, robot, App, revision, installation, operation and run IDs in the
acceptance notes; do not paste secrets there.

Commands use angle-bracketed values such as `<robot-id>` as placeholders. Replace
each with the corresponding ID printed by the earlier command before running it.

## 1. Prerequisites and identity separation

The operator starts the Platform API, local registry/UI and App-capable virtual
topology using the existing local acceptance guides. The Platform Console/API
must be healthy and App installation/runtime delivery enabled. Registry UI is
at `http://localhost:5080`; the registry used by Docker is
`127.0.0.1:5000`.

From the `cdr` shell:

```sh
cd /home/cdr/ringfour/ringfour-platform
uv run --project apps/cli ringfour-cli login
uv run --project apps/cli ringfour-cli whoami
uv run --project apps/cli ringfour-cli org create "AP-13 Publisher cdr"
uv run --project apps/cli ringfour-cli org list
```

Record the new publisher organization ID as `ORG_A`. Keep the `cdr` session in
this workspace. Use an existing publisher organization instead if preferred,
but do not reuse the consumer's organization. Export the actual ID in cdr's
shell so the later commands can use it:

```sh
export ORG_A="<publisher-organization-id>"
```

In a separate terminal logged in as Unix user `ring1`, install the CLI into
ring1's own uv tool environment. This reads the shared source tree and does not
write to cdr's `.venv`:

```sh
uv tool install --isolated /home/cdr/ringfour/ringfour-platform/apps/cli
```

Set the same API URL and public Auth0 CLI settings used by cdr, then authenticate
as the Outlook-backed ring1 identity:

```sh
export RINGFOUR_API_URL=http://localhost:8080
export RINGFOUR_AUTH0_DOMAIN="<configured Auth0 domain>"
export RINGFOUR_AUTH0_CLIENT_ID="<configured CLI public client ID>"
export RINGFOUR_AUTH0_AUDIENCE="https://api.ringfour.eu"
ringfour-cli login
ringfour-cli whoami
ringfour-cli org create "AP-13 Consumer ring1"
ringfour-cli org list
```

Record ring1's distinct user ID and new consumer organization as `ORG_B`.
Confirm `ORG_B != ORG_A` and that cdr is not a member of `ORG_B`. Ring1 keeps
`ORG_B` selected. Ring1's token and config live under `/home/ring1`; never run
uv against cdr's project `.venv` as ring1. Export its actual ID in ring1's
shell:

```sh
export ORG_B="<consumer-organization-id>"
```

For the role check, cdr can invite ring1's Outlook email to `ORG_A` as a Viewer
from Console → Organizations. Ring1 accepts that invitation from Outlook and
confirms Viewer access in `org list`. This adds ring1 to `ORG_A`; cdr remains
outside `ORG_B`, so the run-isolation assertion below still holds. If testing
strictly separate memberships, skip this optional role setup and keep all of
ring1's operations in `ORG_B`.

If ring1's first login reports a keyring error, initialize the Secret Service
in ring1's WSL session using the already installed helper:

```sh
export DBUS_SESSION_BUS_ADDRESS="unix:path=/run/user/$(id -u)/bus"
export PYTHON_KEYRING_BACKEND=keyring.backends.SecretService.Keyring
~/.local/bin/ringfour-unlock-keyring
ringfour-cli login
```

The helper prompts for ring1's own keyring password. Do not use cdr's keyring.

## 2. Prepare two independent App-capable robots

If two numbered App-capable devices are already online, reuse them. Otherwise
the operator starts the numbered App topology from `ringfour-virtual`:

```sh
cd /home/cdr/ringfour/ringfour-virtual
./upn.sh 2 --apps
```

If a singleton already owns the first instance's ports, the operator stops
that overlapping project first after stopping any active App runs. The launcher
checks dirty source trees; inspect each reported diff. Only for an intentional
local preview after that review, the operator may run
`RINGFOUR_ALLOW_DIRTY_APP_SOURCES=true ./upn.sh 2 --apps`. Instance 1 uses the
first port set (`8081`, `10101`); instance 2 uses the next set (`8091`, `10111`).
Each has its own simulator, Agent, Daemon, Docker network and persistent state,
while both share the same Docker Engine and local registry.

Create and enroll one robot in each user's own workspace. As cdr:

```sh
ringfour-cli org select "$ORG_A"
ringfour-cli robot create ap13-cdr-robot
ringfour-cli robot list
ringfour-cli robot enrollment-token <cdr-robot-id>
```

Pass the one-time token directly to the first Daemon. Avoid saving it in shell
history or notes:

```sh
read -r -s -p 'Enrollment token: ' token; echo
RINGFOUR_DAEMON_URL=http://localhost:8081 ringfour-cli daemon enroll "$token"
unset token
RINGFOUR_DAEMON_URL=http://localhost:8081 ringfour-cli daemon identity
```

As ring1, create a robot in `ORG_B` and enroll it to instance 2:

```sh
ringfour-cli org select "$ORG_B"
ringfour-cli robot create ap13-ring1-robot
ringfour-cli robot list
ringfour-cli robot enrollment-token <ring1-robot-id>
```

```sh
read -r -s -p 'Enrollment token: ' token; echo
RINGFOUR_DAEMON_URL=http://localhost:8091 ringfour-cli daemon enroll "$token"
unset token
RINGFOUR_DAEMON_URL=http://localhost:8091 ringfour-cli daemon identity
```

From each user's shell, check the observed inventory:

```sh
ringfour-cli robot capabilities <robot-id> --org <their-org-id>
```

Pass only when each robot is online, its inventory is current, App installations
and runs are supported, its engine target is Linux/amd64, and the IMU capability
is visible. Record each robot ID and its matching numbered Compose project.

## 3. Publish the examples as cdr

The repository contains three runnable examples: Hello World (no sensor), Robot
Check (real IMU read), and Evidence Note (run-scoped artifact). Build uses the
local AP-04 wheel bundle. From cdr's shell:

```sh
cd /home/cdr/ringfour/ringfour-platform
uv run --project apps/cli ringfour-cli app validate /home/cdr/ringfour/robot-check/examples/hello-world
uv run --project apps/cli ringfour-cli app build /home/cdr/ringfour/robot-check/examples/hello-world \
  --wheels /home/cdr/.local/share/ringfour/python-artifacts/0.1.0.dev0
uv run --project apps/cli ringfour-cli app publish /home/cdr/ringfour/robot-check/examples/hello-world \
  --org "$ORG_A" --visibility listed --json
```

Save the returned App ID and revision ID as `HELLO_APP_ID` and `HELLO_V1`.
Repeat for the two other examples:

```sh
uv run --project apps/cli ringfour-cli app validate /home/cdr/ringfour/robot-check
uv run --project apps/cli ringfour-cli app build /home/cdr/ringfour/robot-check \
  --wheels /home/cdr/.local/share/ringfour/python-artifacts/0.1.0.dev0
uv run --project apps/cli ringfour-cli app publish /home/cdr/ringfour/robot-check \
  --org "$ORG_A" --visibility listed --json

uv run --project apps/cli ringfour-cli app validate /home/cdr/ringfour/robot-check/examples/artifact-note
uv run --project apps/cli ringfour-cli app build /home/cdr/ringfour/robot-check/examples/artifact-note \
  --wheels /home/cdr/.local/share/ringfour/python-artifacts/0.1.0.dev0
uv run --project apps/cli ringfour-cli app publish /home/cdr/ringfour/robot-check/examples/artifact-note \
  --org "$ORG_A" --visibility listed --json
```

Confirm the releases appear in the local registry UI and in cdr's App Store.
Publishing must not create an installation or run. A successful push has a
concrete digest; the API release manifest must retain that digest.

## 4. Discover, import, install and configure as ring1

In ring1's shell, select `ORG_B` and discover Hello World:

```sh
ringfour-cli org select "$ORG_B"
ringfour-cli app search "Hello World" --org "$ORG_B"
ringfour-cli app show "$HELLO_APP_ID"
ringfour-cli app import "$HELLO_V1" --org "$ORG_B" --json
ringfour-cli app install "$HELLO_V1" --robot ap13-ring1-robot --org "$ORG_B" --json
```

Save the returned `installation_id` and `operation_id`. Follow install until
device acknowledgement and verify installation created no run:

```sh
ringfour-cli app operation <install-operation-id> --wait
ringfour-cli app installations --robot ap13-ring1-robot --org "$ORG_B"
```

Configure it with a value different from the default:

```sh
cat > /tmp/ap13-hello-config.json <<'JSON'
{"message":"Hello from ring1 on robot two","repeat":20,"interval_ms":1000}
JSON
ringfour-cli app configure <installation-id> --config /tmp/ap13-hello-config.json
```

Follow that operation to `succeeded`. Then start by App ID and explicit robot:

```sh
ringfour-cli app start "$HELLO_APP_ID" --robot ap13-ring1-robot --org "$ORG_B"
```

Record `run_id` and `operation_id`; follow the operation. Inspect the run and
read its output while it is active:

```sh
ringfour-cli app operation <start-operation-id> --wait
ringfour-cli app run <run-id>
ringfour-cli app logs <run-id>
ringfour-cli app logbook --app "$HELLO_APP_ID" --robot <ring1-robot-id> --run <run-id> --org "$ORG_B"
```

Stop the exact run and follow the stop operation:

```sh
ringfour-cli app stop <installation-id> --run <run-id>
ringfour-cli app operation <stop-operation-id> --wait
ringfour-cli app run <run-id>
```

Pass when configured output matches, the run and events belong to ring1's robot
and organization, and stop affects only that run. A second start while an
earlier run is active must be refused by the API/device with no second
container.

## 5. Read a real sensor and fetch a durable artifact

As ring1, import and install Robot Check on the same IMU-capable robot:

```sh
ringfour-cli app import <robot-check-v1-revision-id> --org "$ORG_B"
ringfour-cli app install <robot-check-v1-revision-id> --robot ap13-ring1-robot --org "$ORG_B"
```

Follow install acknowledgement, then start by installation ID. Set
`sample_count` to 3 or 20 through `app configure`. Verify stdout contains
advancing IMU sample stamps and structured Logbook entries. Stop one 20-sample
run quickly with its exact run ID; verify it does not affect another run.

Import and install Evidence Note as well. Start it, then inspect its artifacts:

```sh
ringfour-cli app artifacts <evidence-note-run-id>
ringfour-cli app artifact <evidence-note-run-id> <artifact-id> \
  --output /tmp/ap13-evidence-note.json
cat /tmp/ap13-evidence-note.json
```

Pass when the artifact download verifies the API-declared size and SHA-256 and
contains the configured note. Keep the file outside the App source/build tree.

## 6. Update and rollback without losing the original evidence

Before changing the consumer installation, save the current `revision_id` and
`configuration_revision_id` from its `installed` binding. As cdr, copy Hello
World to a new working directory and publish a new immutable release:

```sh
cp -a /home/cdr/ringfour/robot-check/examples/hello-world /tmp/ap13-hello-v2
python - <<'PY'
import json
from pathlib import Path
p = Path('/tmp/ap13-hello-v2/app.json')
v = json.loads(p.read_text())
v['release'] = '0.2.0'
v['configuration']['defaults']['message'] = 'Hello from Ringfour v2'
p.write_text(json.dumps(v, indent=2) + '\n')
PY
uv run --project apps/cli ringfour-cli app validate /tmp/ap13-hello-v2
uv run --project apps/cli ringfour-cli app build /tmp/ap13-hello-v2 \
  --wheels /home/cdr/.local/share/ringfour/python-artifacts/0.1.0.dev0
uv run --project apps/cli ringfour-cli app publish /tmp/ap13-hello-v2 \
  --org "$ORG_A" --visibility listed --json
```

As ring1, import the v2 revision, update the existing installation and follow
the operation. Confirm the installed binding changes only after device
acknowledgement. Then roll back using the saved v1 revision and configuration
revision IDs:

```sh
ringfour-cli app import <hello-v2-revision-id> --org "$ORG_B"
ringfour-cli app update <installation-id> <hello-v2-revision-id>
ringfour-cli app operation <update-operation-id> --wait
ringfour-cli app rollback <installation-id> \
  --revision <saved-v1-revision-id> \
  --configuration-revision <saved-v1-configuration-revision-id>
ringfour-cli app operation <rollback-operation-id> --wait
```

Pass when rollback creates an installation operation but no run, and the old
run remains linked to its original immutable revision and output.

## 7. Verify role denial, workspace boundaries and two-engine isolation

When the optional Viewer invitation was accepted, ring1 can read the listed App
from `ORG_A` but must not import there (App import requires Developer). Confirm
the structured 403 and that no import was created:

```sh
ringfour-cli app import "$HELLO_V1" --org "$ORG_A" --json
```

From cdr, attempt to read ring1's run and robot. Both must return not-found or
not-authorized because cdr is not a member of `ORG_B`:

```sh
ringfour-cli app run <ring1-run-id>
ringfour-cli robot show <ring1-robot-id>
```

Compare observed Engine containers with both Daemon inventories. Every run
container must have one owner robot, run ID, immutable image digest and exactly
one matching `ringfour-sim-N_default` network. Restart/recreate only Daemon 1
while its App run is active using the operator's AP-08V procedure; verify it
recovers the same run/container and Daemon 2's output continues. Then repeat
for Daemon 2. Do not infer isolation solely from both robots reporting the same
Base101 profile name.

Finally, record the App/revision/import/installation/operation/run IDs, both
workspace/user/robot IDs, image digests, Engine container IDs, network names,
and the observed output/artifact hashes. Note every refused operation and its
API/device error code.
