# AP-07 — install, configure, update and roll back Apps

This slice includes AP-08 as its required engine prerequisite. An installation
pulls/verifies an image and stores its configuration; it never creates a workload
container or run. Hosted start/stop is AP-09, runtime output/HITL is AP-10, and
product UI/operator CLI installation commands remain later milestones.
[Implementation contract](../apps-installation.md). [Evidence](../evidence/AP-07.md).

## 1. Deploy both consumers (operator only)

The workspace AGENTS.md reserves stack rebuild/reload/recreate to the operator.
No stack operation was performed by the agent. The API needs its new
`AppInstallationCommands` migration, and Daemon SQLite automatically applies 0018
(after AP-08's 0017) while retaining its enrollment and deployment namespace.
Do not recreate data volumes or enroll a new robot to upgrade these components.

The feature is disabled by default. Deploy the installation-capable Daemon first
using the opt-in [Compose overlay](../../infra/examples/app-daemon.compose.yaml).
Read [AP-08 socket/GID/network requirements](AP-08.md). The following example
matches the inspected existing singleton project `ringfour-virtual` on
`base101_default`; for numbered projects retain that project's exact name,
network and Agent/Runner/Daemon alias/port environment instead.

```sh
cd /home/cdr/ringfour/ringfour-virtual
export COMPOSE_PROJECT_NAME=ringfour-virtual
export BASE101_NETWORK_NAME=base101_default
# Inspect the socket metadata on the actual engine host, using a disposable helper.
export RINGFOUR_ENGINE_SOCKET_GID="$(docker run --rm --network none \
  --mount type=bind,src=/var/run/docker.sock,dst=/engine.sock,readonly \
  --entrypoint stat alpine:3.20 -c %g /engine.sock)"
docker compose --project-directory . --env-file .env \
  -f compose.yaml -f ../ringfour-platform/infra/examples/app-daemon.compose.yaml config -q
docker compose --project-directory . --env-file .env \
  -f compose.yaml -f ../ringfour-platform/infra/examples/app-daemon.compose.yaml \
  up -d --build daemon
```

The overlay supplies the socket only to the trusted non-root Daemon with its
actual supplementary socket group; it neither chmods the socket nor grants
privileged mode. The owner network is resolved by the engine, never from a
container-local /data bind path. Final multi-robot topology acceptance remains
AP-08V. Keep this overlay in subsequent Daemon Compose commands while opted in.

Then rebuild/reload the API with its opt-in flag:

```sh
cd /home/cdr/ringfour/ringfour-platform
APPS_INSTALLATIONS_ENABLED=true ./up.sh -d api
```

Set `APPS_INSTALLATIONS_ENABLED=true` in the local Platform `.env` if the choice
should persist across future launches. Configure the AP-05 registry policy and
normal Auth0 login before attempting hosted publication/install. No registry
provider or license/public release is inferred. The Daemon offers
`supports_app_installations: true` only in App mode; inventory-only AP-03 sessions
cannot receive install commands. App readiness reports SQLite/engine and does
not require Runner. A missing/inaccessible socket gives `engine: fail`.

## 2. Install a published release

Use AP-06's CLI to publish Robot Check. Obtain an Auth0 access token for audience
`https://api.ringfour.eu` with Developer/Owner membership on the robot workspace.
In the examples, set `API`, `TOKEN`, `ROBOT` and `REVISION` in your terminal;
`REVISION` is the published revision UUID, not an image tag. Keep tokens out of
files/images/logs. Store image layers in the configured registry.

```sh
curl --fail-with-body -sS "$API/v1/robots/$ROBOT/app-installations" \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -H 'Idempotency-Key: robot-check-install-1' \
  --data "{\"revision_id\":\"$REVISION\",\"share_id\":null,\"configuration\":{\"sample_count\":1}}"
```

Expect 202 with `installation_id`, `operation_id`, `run_id: null`. This response
means durable intent, not installed. Save those IDs as `INSTALLATION` and
`OPERATION`. Poll:

```sh
curl --fail-with-body -sS "$API/v1/app-operations/$OPERATION" -H "Authorization: Bearer $TOKEN"
curl --fail-with-body -sS "$API/v1/app-installations/$INSTALLATION" -H "Authorization: Bearer $TOKEN"
curl --fail-with-body -sS "$API/v1/robots/$ROBOT/app-installations" -H "Authorization: Bearer $TOKEN"
```

The candidate progresses separately from `installed`. Success requires operation
`succeeded/applied`, an installed binding naming the exact revision/config/image/
operation and a device observation time, with candidate cleared. Inspect the
engine's four ownership labels from AP-08: installing produces **no App
container**, no run and no execution-slot claim. Several distinct Apps may be
installed on the robot. A second installed copy of the same App is refused with
`installation_exists`; update that installation explicitly. A failed initial
installation can retry with a new key, retaining the installation ID.

For an unlisted release, supply its exact destination-bound `share_id`. An
existing authorized workspace import is reused; otherwise import, installation
and operation commit atomically. A guessed private revision/share is insufficient.
A publisher's listing never gives access to another workspace's robot/history.

## 3. Configure without running

Read `installed.configuration_revision_id` into `CONFIGURATION`. Submit a full
replacement object (validators never merge or insert defaults):

```sh
curl --fail-with-body -sS "$API/v1/app-installations/$INSTALLATION/configure" \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -H 'Idempotency-Key: robot-check-config-2' \
  --data "{\"expected_configuration_revision_id\":\"$CONFIGURATION\",\"configuration\":{\"sample_count\":2}}"
```

Expect a new durable operation and a new immutable configuration revision visible
through the candidate, then through `installed` after device application. Until
success the prior installed configuration remains unchanged. Read any retained
configuration through
`GET /v1/app-installations/$INSTALLATION/configuration-revisions/$CONFIGURATION`.
The same workspace authorization applies. Configure verifies the existing image;
it does not pull it again or create/start a container.

Try `{}`, boolean count, count 0/21, or an extra key: expect `invalid_config` and
no change to the binding. A stale expected ID or concurrent pending edit returns
`stale_installation`. Operator membership can inspect but cannot configure.

## 4. Update and roll back

Publish a distinct release with AP-06, retaining the first immutable release.
POST `/v1/app-installations/$INSTALLATION/update` with a fresh Idempotency-Key:

```json
{
  "expected_revision_id": "CURRENT_INSTALLED_REVISION_UUID",
  "expected_configuration_revision_id": "CURRENT_INSTALLED_CONFIG_UUID",
  "revision_id": "NEW_REVISION_UUID",
  "share_id": null,
  "configuration": {"sample_count": 1}
}
```

Validate against the new schema explicitly; a prior config may be incompatible.
Available release, staged candidate and installed binding remain separate. Missing
fresh Agent inventory/capability/native prerequisites or failed pull/verification
fails the candidate and leaves the prior installed revision/config usable. The
robot must be idle, including App/legacy/local-development activity. Pending App
changes also block new legacy starts; diagnostic starts are disabled on robots
with App installations. Stop existing work before changing its installed binding.

Rollback uses the same current expected IDs and a previously **applied** retained
revision/configuration pair from this installation:

```json
{
  "expected_revision_id": "CURRENT_INSTALLED_REVISION_UUID",
  "expected_configuration_revision_id": "CURRENT_INSTALLED_CONFIG_UUID",
  "revision_id": "PREVIOUS_APPLIED_REVISION_UUID",
  "configuration_revision_id": "PREVIOUS_APPLIED_CONFIG_UUID"
}
```

POST it to `/v1/app-installations/$INSTALLATION/rollback` with a fresh key. It
rechecks compatibility and selects the retained binding while idle. It never
executes the App or rewrites historical configuration. A merely staged/failed
configuration or another installation's configuration cannot be selected.

## 5. Retry, offline and recovery checks

Repeat the exact mutation with its original key: expect the original IDs/result,
even after subsequent state changes. Different input under that key returns
`idempotency_conflict`. Role/ownership are still checked. A new key creates a
new intent only if current expected state permits it.

Offline requests can queue using previously observed engine/support metadata.
A never-dispatched request that reaches its deadline fails without inventing a
device observation. A possible delivery remains uncertain until reconciliation;
an ack means durable receipt, never application. Device preparation/application
checks the deadline and current Agent compatibility. Replacement retaining the
SQLite volume resends an unacknowledged report under its new negotiated session,
using the original report/operation IDs. The sequence/receipt is deduplicated.
Do not restart live stacks for fault injection unless you choose to do so;
the independent harness below performs these faults only against its fixtures.

```sh
uv run --project apps/daemon pytest -q apps/daemon/tests
dotnet test apps/api/tests/Ringfour.Api.Tests
npm test --prefix packages/contracts
python3 packages/contracts/test/openapi_refs.py
uv run --project apps/daemon python tests/e2e/ap07-install.py
```

The harness builds/publishes the checksum-pinned AP-06 template, runs a real
ROS-free Agent, actual Daemon processes and Kestrel/PostgreSQL/Distribution, and
uses a disposable nested engine. It cuts the API after pull authorization, checks
local applied/outbox state, then replaces both API and Daemon and verifies the
same operation/report. It covers configure, incompatible update configuration,
successful update, failed native preparation preserving the old binding,
rollback, two Apps and zero container create/start calls. Its privileged **test
engine** has no production volume or host socket. Tests remove their own stores;
no Platform/virtual infrastructure is touched.

Live Auth0/provider policy, deployed socket/topology and positive simulator IMU
remain operator gates. This acceptance proves advertised compatibility and
installation, not sensor freshness or App execution.
