# AP-18 human acceptance: official Apps, updates, uninstall

This guide exercises the AP-18 API/Daemon/CLI foundation. Studio interaction
and the combined discovery/install/update/result journey are part of AP-21.
Use two authorized workspaces: the configured Ringfour publisher and a normal
consumer workspace. Do not use a production robot for failure injection.

## Before starting

1. Set `APPS_OFFICIAL_PUBLISHER_ORGANIZATION_ID` in the Platform environment
   to the trusted Ringfour publisher workspace UUID. The API refuses public
   (`listed`) publication if this is empty or identifies another workspace.
   If the registry policy is bound to one publisher, set its publisher UUID to
   this same value.
2. Apply both AP-18 API migrations (`AP18OfficialUninstall` and
   `AP18RemovalHistory`) and deploy the updated API and AP-capable
   Daemon. The Daemon must negotiate `supports_app_uninstall`; older sessions
   cannot receive removal commands.
3. Log in as the publisher and consumer separately. Keep publisher releases
   private unless they are intended for every signed-in workspace.

The operator reloads both stacks after the final code changes; the agent does
not perform those operations under the workspace rule.

## Publication visibility

From a normal publisher workspace, publish an App with the default visibility:

```sh
uv run --project apps/cli ringfour-cli app publish PATH
```

Confirm the CLI prints the selected workspace, App, release and private
visibility before publication. The release should be available to its
publisher and authorized share recipients, but absent from another workspace's
Store search. Then request public visibility from that ordinary workspace:

```sh
uv run --project apps/cli ringfour-cli app publish PATH --visibility listed
```

Expect a server `403`; changing client input must not bypass the publisher
entitlement. From the configured Ringfour workspace, publish a new release with
`--visibility listed` and confirm the prompt. In the separate consumer
workspace, verify it is discoverable. Confirm the returned publisher type is
server-derived `ringfour`; a manifest cannot set it. Private releases should
remain private even if their image digest is known.

## Update and rollback

Use an App with two immutable releases and an idle installed robot:

1. Start the older release and confirm an update request is refused until the
   run is stopped.
2. Stop it, stage the newer release with `ringfour-cli app update`, then wait
   for the durable operation with `ringfour-cli app operation OP --wait`.
3. Confirm the installed revision changes only after Daemon confirmation and
   the App remains stopped. Run history must still reference the older release.
4. Use `ringfour-cli app rollback` with a previously applied release and its
   retained configuration revision. Wait for confirmation; verify rollback
   does not start a run and old run snapshots remain unchanged.
5. If using an incompatible release or an unavailable registry in an isolated
   fixture, confirm the prior binding remains usable and retry reports the
   actual operation failure.

## Uninstall and reinstall

Choose one stopped installation; keep another installation of the same App on
a second robot if available. Record its installation ID, current release,
published files and a run ID. Then:

```sh
uv run --project apps/cli ringfour-cli app uninstall INSTALLATION_ID --yes --json
uv run --project apps/cli ringfour-cli app operation OPERATION_ID --wait
```

Verify the confirmation names the App, robot and release. An active run or
competing installation operation must be refused. After successful device
confirmation, verify the selected installation is removed, its run history and
published files remain accessible, and the other robot is unchanged. Offline
delivery remains pending across refresh; API or Daemon replacement must replay
the same operation without applying it twice.

Reinstall the App on the original robot through the normal install flow. The
new installation must have a different ID. Replay or delay the old uninstall
operation in an isolated test and verify it cannot remove the new binding.
Shared image layers are retained; uninstall removes only the installation's
local binding because image layers are shared engine cache data.

Record both workspace IDs, robot/installation/run/operation IDs, release and
image digests, Daemon version, exact commands, operation outcomes and any
missing deployment prerequisite in `docs/evidence/AP-18.md`. Do not include
access tokens or registry credentials.
