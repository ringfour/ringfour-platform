# Combined human acceptance — AP-08, AP-09, AP-10 and AP-08V

Run this after AP-08V implementation checks. The user asked for virtual App
topology implementation before the combined pass. Automated component and
actual-protocol tests are the implementation checks; this pass provides
additional operator confidence. It is not AP-13's full Studio/two-user/two-robot
release acceptance. Studio and operation CLI commands are AP-11/AP-12.

1. **Deploy once.** Operator follows the [AP-07 API/Daemon deployment](AP-07.md#1-deploy-both-consumers-operator-only)
   and [AP-08V topology guide](AP-08V.md) with the latest code. Preserve virt2's
   enrollment, namespace and volumes. API applies AppRunDispatch and
   AppRuntimeEvidence; Daemon applies SQLite through 0020. Readiness reports
   `sqlite: ok` and `engine: ok`. The local registry is already configured.
2. **Check placement.** Only Daemon has the socket and its supplementary socket
   group. Its owner network is base101_default for the current singleton. App
   runtime origin is http://daemon:8081 on that network. Numbered deployment
   qualification remains AP-08V; use that project's own aliases if applicable.
3. **Install/configure.** Follow [AP-07](AP-07.md) with the published Robot Check.
   Installing/configuring produces an operation and binding, no run/container.
   Set sample_count to 20. Preserve the previous revision/configuration IDs.
4. **Run the real IMU App through Platform.** Follow [AP-09](AP-09.md), using
   expected installed IDs. Start through the API, then inspect /app-runs/{id} and
   its output. Expect 20 advancing IMU samples, completion and succeeded/exit 0.
   This is a managed run, distinct from the earlier direct docker demonstration.
5. **Exercise a longer run.** Build/publish/install the [AP-10 runtime fixture](AP-10.md#prepare-the-runtime-test-app).
   It waits for human input, giving time to inspect the container and test Stop.
   Starting another App on virt2 must conflict while it is active.
6. **Prove replacement.** Record container ID/StartedAt, have the operator replace
   only Daemon with the same data, and confirm the same run/container survives.
   Stop it through the exact run ID. Start again, repeat the previous run's Stop,
   and verify the newer run continues. Disconnection never implies stopped.
7. **Prove evidence.** Inspect stdout/stderr with byte cursors. Download the
   fixture artifact: original bytes survive source mutation/deletion. Follow the
   same run/event IDs from global, App and installation Logbook filters.
8. **Prove human decisions.** Submit yes while Daemon is stopped: submitted stays
   provisional. After operator replacement it becomes applied exactly once and
   the App finishes. On another run, Stop cancels the prompt. An engine outage
   retains unknown state; it does not invent cancellation or approval.
9. **Prove recovery and refusal.** Follow [AP-10 recovery checks](AP-10.md#recovery-and-negative-checks),
   including API outage after local publication, late evidence delivery, wrong
   run/workspace reads, stale configuration and competing answers. Reuse the
   [AP-07 update/rollback checks](AP-07.md): failures retain the prior binding;
   earlier runs retain their original digest/configuration and evidence.
10. **Record the outcome.** Save sanitized run/operation/installation IDs, image
    digest, container ID/StartedAt and pass/fail observations. Never save tokens
    or full inspect environment. Record unperformed checks as pending.

11. **Qualify topology and shutdown.** Complete the single and numbered
    Compose, Engine socket/GID, Daemon replacement, network/DNS isolation and
    safe-down checks in [AP-08V](AP-08V.md). Verify two different numbered
    networks and Daemon namespaces. Do not treat this as AP-13's cross-user
    authorization test.

Automated counterparts from Platform:

```sh
uv run --project apps/daemon python tests/e2e/ap09-runs.py

```

These harnesses manage disposable engines/processes and never reload either live
stack. The AP-09/AP-10 harnesses also rerun installation/configuration/update/
rollback acceptance. They use the actual Agent protocol and runtime clients;
only the live IMU check above proves simulator sensor freshness.
