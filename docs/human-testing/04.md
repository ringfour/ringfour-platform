# Human testing — milestone 04 local Runner

This guide covers the local diagnostic slice and the Balena Runner smoke test.
The Odin device passed the non-motion Runner smoke; SDK/Agent robot execution is
not part of that test. Run commands from the repository root.
The integrated test creates a test robot in the selected organization; temporary
containers and volumes are removed, but that robot remains in the platform.

## Prerequisites and setup

Complete the Auth0 and enrollment setup in guides 01–03. Docker, uv and Node
are required. Use an owner or developer account and select an organization.
Port 18084 must be free for the isolated test. Set a random shared Runner secret
for both services; never paste it into evidence or commit it:

```bash
export RUNNER_AUTH_TOKEN="$(openssl rand -hex 32)"
docker compose -f infra/compose/docker-compose.yml up -d --build
uv run --project apps/cli ringfour-cli login
uv run --project apps/cli ringfour-cli org list
uv run --project apps/cli ringfour-cli org select <organization-id>
```

Use the same value when recreating only one service. Missing Runner credentials
make its readiness check fail. For a deployed device, provision a separate
high-entropy secret through device configuration, not the source tree.

## Run the local end-to-end check

```bash
bash scripts/quality.sh
bash tests/e2e/04-runner.sh
```

Expect all component checks to pass, followed by `PASS` lines for the hello
fixture, daemon restart and stop, and Runner restart reconciliation. The test
uses the real API, PostgreSQL, daemon, Runner, SQLite, WebSocket and private
HTTP; it checks Runner's non-root user, read-only staging mount, no host port,
no Docker socket and rejection of an unauthenticated request. The hello result
contains `Hello from Ringfour Runner` and exit code 0. The long fixture is
cancelled; after a separate Runner restart, interrupted running work is reported
failed with `interrupted_unknown_outcome`, not relaunched. Test-only containers
and their three named volumes are deleted on exit.

## Use the diagnostic commands manually

Enroll a daemon for a robot using guide 02, then run:

```bash
uv run --project apps/cli ringfour-cli robot fixture-start <robot-id> hello
# Record the returned operation id; it is also the execution id.
uv run --project apps/cli ringfour-cli robot operation <robot-id> <operation-id>
uv run --project apps/cli ringfour-cli robot fixture-inspect <robot-id> <execution-id>
# Record the returned inspection operation id, then retrieve its result:
uv run --project apps/cli ringfour-cli robot operation <robot-id> <inspection-operation-id>
```

The start and inspect commands enqueue hosted operations, so poll `robot
operation` until `state` is `succeeded` or `failed`. Inspection returns an
execution snapshot and a base64 output chunk. The `offset` and `next_offset`
values count bytes and may not exceed 65536. Pass `--stream stderr`, `--offset N` and `--limit N` to
`fixture-inspect` for another chunk; each read is limited to 16384 bytes and
each stream retains at most 65536 bytes. `eof` and `truncated` describe the
stored output.

For a stop, start `long`, wait until its inspection reports `running`, then:

```bash
uv run --project apps/cli ringfour-cli robot fixture-stop <robot-id> <execution-id>
uv run --project apps/cli ringfour-cli robot operation <robot-id> <stop-operation-id>
```

Inspect again until the execution is `cancelled`. A second active start returns
a failed operation with a Runner conflict. Runner command requests require a
developer or owner; stop additionally allows an operator. Requests for another
organization's robot remain inaccessible. Virtual environments isolate Python
dependencies; this v0.1 system assumes trusted code.

## Verify on a Balena device

Use this only with an enrolled robot and while the Platform API is reachable.
These diagnostic fixtures do not use the RoboCore Agent or move the robot. From
the platform repository, with `.auth.env` and an authorized CLI login ready:

```bash
export RINGFOUR_ROBOT_ID=<robot-id>
bash tests/e2e/04-device.sh hello
```

Expect `HELLO execution … state succeeded exit 0` and the hello output. The
script prints the execution ID; save it to check persisted output later. To
check daemon restart and stopping work:

```bash
HELLO_ID=<paste-hello-execution-id>
bash tests/e2e/04-device.sh start-long
LONG_ID=<paste-long-execution-id>
bash tests/e2e/04-device.sh overlap
balena device restart <device-uuid> --service ringfour-daemon
bash tests/e2e/04-device.sh inspect-running "$LONG_ID"
bash tests/e2e/04-device.sh stop "$LONG_ID"
```

Expect the overlapping start to fail with `execution_conflict`, then the
original execution to be `still running` and finally `cancelled`. For Runner
restart recovery:

```bash
bash tests/e2e/04-device.sh start-long
INTERRUPTED_ID=<paste-new-long-execution-id>
balena device restart <device-uuid> --service ringfour-runner
bash tests/e2e/04-device.sh inspect-failed "$INTERRUPTED_ID"
bash tests/e2e/04-device.sh verify-hello "$HELLO_ID"
```

Expect `interrupted_unknown_outcome`, followed by the earlier hello output and
exit 0. The long fixture sleeps for up to five minutes; if a check is
interrupted, stop any remaining fixture with `bash tests/e2e/04-device.sh stop
<execution-id>`. The physical test retains execution and operation history;
it does not reset the robot, purge volumes, or delete data. Check the robot
remains online in the Console after finishing. See `docs/evidence/04.md` for the
observed Odin device and image versions.
