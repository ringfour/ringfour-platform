# Milestone 08 human testing

Status: **mission-authored entries are locally integrated**. No automatic
mission, human-intervention or Agent motion producer, CLI history query or
Console timeline has been implemented. Milestone 07 also remains incomplete.

To validate the current example contracts from the Platform repository root:

```sh
npm --prefix packages/contracts test
```

The output should include a passing proposed Logbook fixture test. This checks
schema examples and rejection of invalid fields, not event durability or replication.

To exercise ingestion through real HTTP and PostgreSQL on an isolated stack,
configure `.auth.env` and sign in through the CLI, then run:

```sh
bash tests/e2e/08-ingestion.sh
bash tests/e2e/08-outbox.sh
RINGFOUR_TEST_LOGBOOK=1 bash tests/e2e/07-cli-dev.sh
RINGFOUR_TEST_LOGBOOK=1 RINGFOUR_TEST_LOGBOOK_OFFLINE=1 bash tests/e2e/07-cli-dev.sh
```

The script builds the API, creates a temporary database, organization and
robot, enrolls a test credential, and inserts a test operation. It checks
unauthenticated access, a sequence gap, successful ingestion, API restart,
replay and conflicting replay. The expected final output begins `PASS: actual
HTTP ingestion`. It removes its temporary containers and network. It does not
exercise a daemon outbox or a physical device. See
[the contract](../logbook-contract.md) for the endpoint and event format.

The second command starts a real daemon and explicitly inserts synthetic events
into its outbox while the API is stopped. It restarts the daemon, restarts the
API and checks that both events arrive once and the local queue is acknowledged.
Its expected output begins `PASS: durable daemon outbox`. This is not a mission
history test: operation state changes are not yet wired to produce events.

The third command builds temporary wheels from the sibling SDK and the separate
Platform runtime package, installs both in an isolated real Runner environment
using a hash-pinned lock, and uses the CLI
to sync and run a development mission. That mission calls
`logbook.info("Inspection skipped", station="B", reason="Operator reported maintenance")`.
The test checks that the daemon queues the entry and the Platform stores its
message, fields and execution association. It requires Docker, `.auth.env`, an
existing CLI login and the sibling `ringfour-sdk` and `missions` repositories.
It removes its containers, volumes and temporary files. This is not yet a
physical robot test and does not verify motion history.

The fourth command runs the same author-entry test with the Platform stopped
when the mission writes the entry. It verifies that the mission finishes after
the daemon durably accepts the entry, then restarts the Platform and checks the
entry is replicated with the expected execution and actor.

For a deployment, the Runner must receive `RUNNER_LOGBOOK_URL` pointing to the
daemon control listener on the robot's private network, and the daemon and
Runner must share their existing private `RUNNER_AUTH_TOKEN`. The mission must
pin the `ringfour-platform-runtime` integration wheel in its dependency lock.
The standalone SDK remains independent. The new entry appears in hosted storage
and Console's **Logbook** view. A Logbook CLI is not yet available.

The complete demo mission must exercise available Logbook capabilities and
document their expected output. The robot is lifted:
do not assume its wheels touch the ground or that sensor and odometry values

it does not require odometry updates. Other Agent motion paths, mission lifecycle

With the updated API and robot services configured as described in base101's
`ringfour-balena-logbook-integration.md`, push and run the demo from this
checkout:

```sh
uv run --project apps/cli ringfour-cli ../missions/logbook-demo push --robot <robot-name-or-id> --start --follow
```

In Console, open **Logbook**, refresh, and select the demo execution for the
author's capability and wheel-test entries. Agent
`motion.accepted` and `motion.completed` records, if teleop starts and closes
successfully, appear under **Unlinked robot events** for that robot because they are not
currently linked to the execution. A `motion.stop_verified` row
requires measured-stop evidence from the Agent; no row should be interpreted as
proof of a stop. A refused or failed operation can instead produce
`motion.refused` or `motion.failed`. The Agent-local owner and session do not
identify the Platform user or mission automatically. The demo has not been
tested on base101.

## Console Logbook

Start the updated local API and Console, sign in, then select **Logbook** in the
main sidebar. Choose a workspace and use the **Mission**, **Robot**, and
**Human** filters to narrow the execution list. Click a mission, human, or
robot label in a row to apply that filter; click its timestamp to open the
execution. Clear filters with the **×** buttons or the **All** options. Successful
executions are shown in teal and failures in red. Use **Refresh** to reload.

The selected execution shows a chronological timeline across the available
content area. Event icons and colors distinguish mission notes, activity, successful
outcomes, failures and incomplete history; unknown events remain neutral.
Expand an event to see its type, context and structured fields; expand **Execution output** to see
stdout and stderr. The API currently exposes user IDs, not names: your account
is shown as **You**, other users by ID, and missing actors as **Unknown user**.
Each row also shows **as: role (current)** using the user’s present workspace
role; users no longer in the workspace show **unknown**. This is not a record
of the role at execution time. Direct script runs appear as **Direct run**.

For Agent motion or other entries without a known mission execution, clear the
mission and human filters and choose **Unlinked robot events** for a robot. The
UI does not infer mission or run ownership for these entries. Authenticated
organization membership is required; entries from other organizations are not
returned. Agent motion coverage and human-intervention production remain
incomplete.

## Local Agent journal transfer

From the Platform repository, with the sibling Agent, SDK and testing checkout
installed as described in `../ringfour-testing/README.md`, run:

```sh
uv run --project apps/daemon --group dev python tests/e2e/08-motion-handoff.py
```

It prints `Agent journal to daemon inbox: restart and lost acknowledgement
passed` if the socket transfer survives the simulated crash and restart. It uses
a synthetic event, temporary local databases and no robot.

To exercise the same path through the Platform API and PostgreSQL, run
`bash tests/e2e/08-motion-platform.sh`. This needs Docker, `.auth.env`, an
existing CLI login, the local `ringfour-agent:c-preview` image and the sibling
Agent and testing checkouts. It creates isolated containers and a temporary
volume, then cleans them up. A synthetic Agent task produces accepted,
measured-stop and completed records. It does not observe or command a real
stop. The task and teleop producers are enabled only with the local journal
socket configured. On overflow or an unclean boot, `motion.history_incomplete`
indicates that records may be missing; it does not recover lost outcomes.
