## 1. Configure the registry and reload the API

Set these values in the Platform deployment environment (`.env` for local
server Compose). Keep secret values outside Git and chat:

```dotenv
APPS_REGISTRY_HOST=registry.example.com
APPS_REGISTRY_REPOSITORY_PREFIX=ringfour
APPS_REGISTRY_ANONYMOUS_PULL=true
```

Replace both example values with the actual image registry authority (including
port if needed) and repository/prefix. The registry authority must be reachable
from both the hosted API and the robot deployment engine. The prefix matches itself or children at
a slash boundary. Empty policy rejects publication. The deployed server uses
HTTPS. Explicit anonymous pulls require publicly readable images.

For a private registry set `APPS_REGISTRY_ANONYMOUS_PULL=false`, set
`APPS_REGISTRY_PUBLISHER_ORGANIZATION_ID` to the publisher workspace UUID, and configure
`APPS_REGISTRY_TOKEN_ENDPOINT`, `APPS_REGISTRY_SERVICE`,
`APPS_REGISTRY_USERNAME` and `APPS_REGISTRY_PASSWORD`. The registry must use
Distribution Bearer challenges with that exact realm/service, and issue
pull-only tokens lasting at most five minutes. Do not put a long-lived personal
token into an App. A private policy without a publisher binding fails closed;
other workspaces consume its releases through authorized imports rather than
republishing guessed image digests. A registry requiring Basic credentials directly on pulls
without a supported token service is not a supported private policy.


## 2. Publish and discover a real release

Use a manifest for an actual image already pushed to the allowed repository.
Its target must reference a concrete Linux amd64/arm64 image digest, not a tag
or multi-platform index. All declared targets must be verifiable. The schema
fixture's `aaaa…` digest is illustrative and cannot be published as a real image.
Use the manifest/configuration rules in [manifest v1](../apps-contract.md).

Obtain an Auth0 access token through the normal login flow. In a local shell,
set `API_URL`, `PUBLISHER_ORG` and `ACCESS_TOKEN` without printing the token.
Create `publish.json` containing `{"manifest": <your manifest>, "visibility":
"listed"}`. Then:

```sh
curl --fail-with-body "$API_URL/v1/organizations/$PUBLISHER_ORG/app-revisions" \
  -H "Authorization: Bearer $ACCESS_TOKEN" \
  -H 'Idempotency-Key: ap05-publication-1' -H 'Content-Type: application/json' \
  --data-binary @publish.json
```

Expect 201 with immutable revision/App IDs, manifest digest, publisher, actor and
publication time. Repeating the same request/key returns the original result;
a different key with identical release content resolves to that same revision.
Changed content under the same key returns `idempotency_conflict`; changed
content at the existing App/release under a new key returns `revision_conflict`.
Changing registry state cannot invalidate an already committed retry response.

As a member of consumer workspace B, with its own token:

- `GET /v1/store/apps?organization_id=<B>&q=<key>&limit=1` finds listed Apps;
  follow `next_cursor` with the same query. Limits are 1–100, default 50.
- `GET /v1/apps/<app_id>`, `/v1/apps/<app_id>/revisions`, and
  `/v1/app-revisions/<revision_id>` return only authorized metadata/revisions.
- Publishing to A with B-only membership returns 404. A member with only the
  Operator role receives 403 for publication/import/share mutations.

Publication verifies actual registry bytes/configuration. A wrong digest,
wrong architecture, index, redirect, unallowed repository or unavailable
registry returns a bounded error and creates no App/revision/idempotency result.
There are no layer uploads to Platform object storage.

## 3. Import and directly share

With B's Developer/Owner token, POST
`/v1/organizations/<B>/app-imports` with an `Idempotency-Key` and
`{"revision_id":"<listed revision>","share_id":null}`. Expect 201. Repeated
keys and different keys for that workspace/revision retain the original import
ID, publisher, actor and provenance. Read B's library at
`GET /v1/organizations/<B>/app-imports`.

For an unlisted revision, A's Developer/Owner posts
`/v1/app-revisions/<revision>/shares` with a new key and
`{"destination_organization_id":"<B>","expires_at":"<future UTC timestamp>"}`.
Use the returned share ID explicitly in B's import request. An unknown/wrong
destination grant returns scoped 404; an expired/revoked grant returns
`share_expired`/`share_revoked`. Omitting the grant for a revision already
readable through a valid share returns `share_required`; a guessed inaccessible
revision stays scoped 404.

A revokes using POST `/v1/app-shares/<share>/revoke`, with an idempotency header
and **no body**. Existing imports remain usable and keep historical provenance;
new imports cannot use that revoked grant. Confirm C cannot use B's share and
neither A nor C can list B's private imports, robots or history. A listed App
does not expose every unlisted revision under that App.

## 4. Understand machine registry grants

`POST /v1/device/app-registry-grants` requires robot credentials, current
`x-ringfour-device-session` and negotiated App support. It accepts
`{operation_id, revision_id, image}` for that robot's authorized preparation
candidate. It returns exact image/robot/revision/operation binding, expiry and
anonymous or short-lived Bearer authority with `Cache-Control: no-store`.

AP-05 creates no live install operations. Do not fabricate candidate rows in the
running database to exercise this route. The isolated harness below supplies a
controlled AP-07 preparation fixture in a disposable DB. AP-07 will connect its
actual installation writers. Unknown/other-robot/completed operations, wrong
targets, expired deadlines and replaced sessions cannot obtain a grant.
Credential revocation during registry verification is rechecked before response.
Repository-scoped credentials still require the Daemon to enforce exact digest.
