# AP-08 — owner-scoped engine prerequisite for installation

AP-07 explicitly requires AP-08. This slice supplies the executor and recovery
boundary first; it does not enable hosted App install/start commands.
See [engine design](../apps-engine.md) and [evidence](../evidence/AP-08.md).

## Operator deployment

The agent never reloads either stack. To deploy this Daemon slice, the operator
must rebuild/recreate the virtual Daemon through the appropriate virtual stack
script after supplying these settings/mounts (AP-08V owns final topology):

- `RINGFOUR_APPS_ENABLED=true`
- `RINGFOUR_ENGINE_SOCKET=/var/run/docker.sock`, an operator-mounted engine socket
- the socket's supplementary group GID for the existing non-root Daemon user
- `RINGFOUR_APP_NETWORK=<owner network on that same engine>`
- the reachable `RINGFOUR_AGENT_URI` and verified native prerequisite settings
- the existing persistent daemon-data volume, enrollment and namespace

Do not change socket permissions or grant a privileged Daemon/App. The socket
itself grants engine administration to its trusted Daemon. No App receives it.
Do not use a container-local /data bind path as an engine host path. This slice
copies a root-owned mode-0444 configuration file into the App before start.
The App must have a numeric non-root image user and an image entrypoint.

App readiness uses SQLite and the engine, independent of Runner. With the socket
missing/inaccessible it returns 503 with `engine: fail`. Without App mode, legacy
readiness and workflows remain unchanged. Inventory in App mode reads the actual
engine OS/architecture; operator declarations remain the legacy AP-03 mode.
The read-only status page shows saved App run observations/output in App mode.

## Independent verification without reloading stacks

From Platform:

```sh
uv run --project apps/daemon pytest -q apps/daemon/tests
uv run --project apps/daemon python tests/e2e/ap08-engine.py
```

The second command creates only disposable nested Docker/registry fixtures.
It requires Docker and the existing local alpine:3.20 dependency image, creates
privileged **test engines**, and removes those exact test containers and stores.
It never mounts the host engine socket into its workload and never operates
Platform/virtual infrastructure. It exercises the actual Engine REST protocol,
not a mock. Test-only faults discard actual create/start responses.

Expect pull to create zero containers, recovery to find one exact owned container,
replacement Daemon processes to retain it without a second launch, and stop to
seal stdout/stderr before removal. The fixture App prints its count-2 config and
stderr evidence. Component tests cover foreign ownership/image/network/ID,
duplicate matches, conflicting names, unavailable socket and a lifetime writer
fence. Old-run replay never creates a new execution. Missing possibly started
containers become interrupted with unknown exit/end time; they are not relaunched.

The executor API is internal. Human install/configuration endpoints arrive in
AP-07; hosted starts/stops arrive in AP-09, runtime delivery in AP-10. These are
not shipping CLI install/start commands. Positive live Robot Check IMU and hosted
registry/Auth0 publication remain separate pending gates from AP-06.
