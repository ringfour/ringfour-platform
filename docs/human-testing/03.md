# Human testing guide — milestone 03 (connectivity)

Everything a human can use and verify after milestone 03: the daemon's
authenticated WebSocket to the platform, observed online/offline status, the
durable diagnostic operation, retry/idempotency behavior, interruption and
restart recovery, and revocation cutting the live connection.

Milestones 01–02 functionality (login, organizations, robots, enrollment)
still applies — see `docs/human-testing/01.md` and `02.md`. Prerequisites are
the same: stack running (`docker compose -f infra/compose/docker-compose.yml
up -d --build`), CLI environment sourced from `.auth.env`, and `ringfour
login` approved as account 1 (the owner), with an enrolled robot (guide 02,
steps 1–3).

## 1. Watch the daemon connect by itself

No command is needed: the daemon process polls for enrollment and opens the
WebSocket on its own. Within a few seconds of `daemon enroll` (or immediately
after container start when already enrolled):

```bash
uv run ringfour robot status <robot-id>
```

Expected:

```
Robot:            <robot-id>
  Status:           online
  Last seen:        2026-11-10T…Z   (refreshes every 15 s)
  Daemon version:   0.1.0
  Protocol version: 1
```

## 2. Console status inspector

```bash
open http://localhost:5173
```

Sign in, open **Robots**, click a robot's name. The detail panel now has a
**Device status** section with an `online`/`offline` badge, last seen time and
the observed daemon/protocol versions; it refreshes every 5 seconds. Any org
member can view it (read-only).

## 3. Run a diagnostic operation

Any developer or owner can create the v1 diagnostic operation (operators get
`403 forbidden`):

```bash
TOKEN=$(uv run python - <<'PY'
from ringfour_cli.auth import TokenStore
from ringfour_cli.config import load_settings
print(TokenStore().load(load_settings())["access_token"])
PY
)

curl -s -X POST "localhost:8080/v1/robots/<robot-id>/operations" \
  -H "authorization: Bearer $TOKEN" -H 'content-type: application/json' \
  -d '{"kind":"diagnostic.noop","payload_version":1,"payload":{}}'
```

Expected: `201` with the operation in state `queued`, a `deadline_at` one
minute out, and your user id in `requested_by`. Follow it to the terminal
state:

```bash
curl -s "localhost:8080/v1/robots/<robot-id>/operations/<operation-id>" \
  -H "authorization: Bearer $TOKEN"
```

Expected within a second or two: `state: succeeded`, `acknowledged_at` set,
`result: {"noop": true}`. Nothing else runs — this is the protocol's
authenticated no-op proving the whole path works.

## 4. Safe retries with Idempotency-Key

Repeat the creation with a key, then repeat it identically:

```bash
curl -s -o /dev/null -w '%{http_code}\n' -X POST \
  "localhost:8080/v1/robots/<robot-id>/operations" \
  -H "authorization: Bearer $TOKEN" \
  -H 'content-type: application/json' \
  -H 'idempotency-key: my-key-1' \
  -d '{"kind":"diagnostic.noop","payload_version":1,"payload":{}}'
# → 201, operation A

curl -s -w '\n%{http_code}\n' -X POST \
  "localhost:8080/v1/robots/<robot-id>/operations" \
  -H "authorization: Bearer $TOKEN" \
  -H 'content-type: application/json' \
  -H 'idempotency-key: my-key-1' \
  -d '{"kind":"diagnostic.noop","payload_version":1,"payload":{}}'
# → 200, the SAME operation A (same id), not a new one
```

Send the same key with a different body and you get `409 conflict`. Records
expire after 24 hours.

## 5. Offline after interruption, online after reconnect

```bash
cd ../../   # repo root
DAEMON=$(docker compose -f infra/compose/docker-compose.yml ps -q daemon)
NET=$(docker inspect -f '{{range $n, $x := .NetworkSettings.Networks}}{{$n}}{{end}}' "$DAEMON")
docker network disconnect "$NET" "$DAEMON"
```

Wait ~50 seconds, then:

```bash
uv run ringfour robot status <robot-id>     # Status: offline
```

Status is derived by the API from its own receive-time freshness window
(45 seconds); the device never has to say goodbye. Create an operation now —
it stays `queued`. Then:

```bash
docker network connect "$NET" "$DAEMON"
```

The daemon's reconnect backoff (1 s → 30 s cap, jittered) finds the platform
again within half a minute; status flips back to `online` and the queued
operation runs exactly once.

## 6. Restart recovery without duplicate effects

```bash
docker compose -f infra/compose/docker-compose.yml restart daemon
uv run ringfour robot status <robot-id>     # online again within ~a minute
```

Create another operation; it succeeds. The daemon's local SQLite
(`device_operations`) holds exactly one row per operation id — replay after
restart never re-executes an effect. You can look:

```bash
docker compose -f infra/compose/docker-compose.yml exec -T daemon python -c \
  "import sqlite3; print(sqlite3.connect('/data/ringfour.db').execute('SELECT operation_id, state FROM device_operations').fetchall())"
```

## 7. Revocation cuts the live connection

```bash
CRED=$(uv run ringfour daemon identity | grep Credential: | awk '{print $2}')
uv run ringfour robot revoke <robot-id> "$CRED"
```

Expected: the platform closes the daemon's WebSocket immediately; the daemon
keeps retrying with backoff and is denied every time (the credential is
revoked). Within ~45 s `robot status` reads `offline`. The daemon is still
enrolled — `daemon identity` is unchanged — it just cannot talk to the
platform until an owner rotates the credential and re-enrolls it.

## 8. Cross-account isolation (account 2)

Log in as account 2 (guide 01, step 5). If account 2 is an operator in your
org it can read status and operations but `POST …/operations` returns
`403 forbidden`; non-members get `404 not_found` on every robot route.
Restore account 1 afterwards (`uv run ringfour login`).

## Troubleshooting

| Symptom | Cause / fix |
|---|---|
| Status stays `offline` right after enroll | Give it a few seconds — the daemon polls for enrollment every 5 s and connects automatically; check `docker compose … logs daemon`. |
| `403 forbidden` creating an operation | Operator role cannot create operations; developers and owners can. |
| `409 conflict` with an idempotency key | The same key was already used with a different request body — pick a new key. |
| Operation stuck in `queued` | The robot is offline; it runs on reconnect. If it sits past `deadline_at`, the sweeper fails it with `deadline_exceeded`. |
| Status `offline` but daemon looks fine | Heartbeat interval is 15 s and the offline threshold 45 s — allow up to ~a minute before worrying. |
| After revocation, endless "reconnecting" logs | Expected: the daemon retries until a fresh credential is enrolled (`robot rotate` issues a new secret; re-run `daemon enroll` needs a new enrollment token on a fresh robot for now). |
