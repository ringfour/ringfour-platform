# AP-17 human acceptance guide

Status: prepared for acceptance; not yet accepted. The live-settings runtime
wheel/template pins and a newly published v2 App image are prerequisites for
the device-to-App scenarios. Do not treat UI rendering or mocked/component
results as proof of device behavior.

## Before starting

Use two separate Ringfour users: the main `cdr` account and `ring1`. Confirm
that each user has access to the intended consumer workspace, and that the
publisher account can publish a v2 release. Use `ringfour-cli whoami` and
`ringfour-cli org list` in each user shell to confirm identity and workspace.
Do not share CLI token stores between users.

The pinned `ringfour_runtime` 0.1.1.dev0 bundle and Robot Check template 0.2.0
are prepared locally. The template has already validated and built as an amd64
image. As the publisher, build/publish a release from the prepared template or
rebuild it from the pinned inputs after API reload. The App declares a bounded
startup value and one live value, acknowledges initial settings before
behavior depends on them, makes its handler idempotent, and publishes a small
summary artifact. Record its immutable release ID and image digest.

The API and Daemon source changes require the operator to reload the Platform
API and the `ringfour-virtual` Apps stack. Workspace instructions reserve these
operations for the operator. From the respective repositories, use:

```sh
cd /home/cdr/ringfour/ringfour-platform
APPS_INSTALLATIONS_ENABLED=true APPS_LIVE_SETTINGS_ENABLED=true ./up.sh -d api

cd /home/cdr/ringfour/ringfour-virtual
./up.sh --apps -d
```

The Console dev server should pick up source changes through its normal hot
reload. Sign in again if its Auth0 session expires. Do not recreate database or
object-storage volumes for this acceptance.

## App detail and target selection

1. Sign in to Studio as `cdr`; select the consumer workspace.
2. Open **Apps**. Confirm imported Apps remain listed and opening an App name
   navigates to `/apps/{appId}/overview` in the same workspace. Search by App
   name and robot name; confirm the library keeps each App as one row and shows
   concise installation targets without repeating its configuration editor.
3. Open an App installed on one robot. Confirm that robot is selected by
   default, and that the page does not start the App merely by opening it.
4. Install the same App on a second robot. Open the App again. Confirm the
   robot selector requires a concrete choice before showing robot-specific
   controls. Select each robot and confirm the URL preserves the installation
   ID when switching Overview, Settings, Files and Activity.
5. Use browser Back/Forward and reload a deep link. Confirm the workspace,
   App, section and selected installation are restored.
6. On a narrow browser width and with keyboard-only navigation, reach the App
   selector, section links and actions. Confirm visible focus and that the
   selected tab exposes `aria-current="page"`.
7. From Home, open an App link under **Apps in use**. Confirm one App with
   multiple robot assignments is grouped under one App identity and each robot
   opens the matching installation. Offline assignments must say “Last
   reported” rather than implying current execution.
8. In a workspace with no enrolled robots, confirm Home shows one setup path.
   If an App is already imported, its action should open **Apps**; otherwise it
   should open **App Store**. In both cases, the primary action should open
   **Robots**, and Home must explain that installing does not start an App.

## Startup configuration and live settings

1. Open **Settings** for each robot installation. Confirm the startup section
   explains that values apply on the next process start and the live section is
   separate. Compare the selected next-start values with values last confirmed
   by the current process; these can differ and must be labeled separately.
   Change a value, then use **Discard edits** and confirm it returns to the last
   loaded value. Change another value and navigate to another Studio section;
   confirm the browser warns before discarding it.
2. Change a startup value while the App is running. Confirm the ordinary
   configure action refuses the active run and leaves that process untouched.
   Stop the exact run, save the startup configuration, then start a new run.
   Confirm the new run receives the updated value.
3. With no active run, change live settings and save. Confirm Studio says
   **Saved for next start**, not “applied.” Refresh the page and confirm the
   selected values remain. Start the App and confirm it reports initial
   application before performing settings-dependent work.
4. While the App is running, change a live value. Confirm the request is shown
   as pending with the exact robot context. Do not treat the Save click or the
   HTTP 202 response as confirmation. Wait for the App acknowledgement and
   confirm Studio shows the resulting state.
5. Configure the example App to reject an otherwise schema-valid value. Confirm
   the safe rejection reason is visible, the previous confirmed value remains,
   and the next-start selection is unchanged.
6. Submit an invalid type or out-of-range value. Confirm it is rejected before
   delivery to the App and is associated with the affected field where
   possible.
7. While a live application is pending, attempt another change. Confirm Studio
   disables its fields and Save action with an explanation. Stop the exact run
   if necessary; do not imply a timeout undid App-side effects.
8. Sign in as `ring1` with a viewer/operator role. Confirm it can inspect state
   according to workspace policy but cannot save settings. Confirm a publisher
   in another organization cannot inspect this installation's values.

## Files and Activity

1. Update to the Camera Snapshot Loop release from
   `/home/cdr/ringfour/robot-check/examples/spin-photos` on a robot that
   advertises cameras. Start it and confirm the first photo is captured
   immediately and later photos arrive every 30 seconds. The App must not
   request teleop or send motion commands. After its configured photo limit,
   confirm it remains running until stopped. Stop the exact run through Studio
   or `ringfour-cli app stop <installation-id> --run <run-id>`. Confirm the stop
   operation completes, the run reaches `stopped`, and `reports/summary.json`
   is published after graceful shutdown.
2. Run the example on both robots and publish the same relative artifact path
   from each run with different content.
3. Open the App's **Files** section. Confirm both files appear with robot,
   run state, publication time and size. The identical paths must remain
   separate entries.
4. Filter by a robot installation, a run, and a folder/path prefix. Confirm
   every filter narrows results correctly. Open synthesized folders and use
   their breadcrumbs to move back up. Confirm the folder counts are labeled as
   loaded results and load more pages to discover folders not on the first
   page. Load additional pages and confirm entries are not duplicated or
   skipped. Try an unsafe path prefix and confirm the API rejects it.
5. Download both same-path files. Confirm each has its original bytes and that
   size and SHA-256 verification succeeds. Delete or change the App source and
   confirm already published artifacts remain downloadable.
6. Open **Activity**. Confirm it shows readable App Logbook event titles,
   robot and time, can be filtered by selected installation and run, and links
   to exact runs. Expand event details to inspect durable event and operation
   IDs. Open the same run from global **Logbook** and confirm its event IDs and
   settings outcomes match. Submitted HITL responses must remain distinct from
   device-applied responses.
7. Confirm empty Files and Activity states are explicit. Files describe
   published outputs, not an editable App disk or persistent installation
   filesystem.

## CLI parity

Run these commands in each account's own shell and compare the selected IDs
with Studio:

```sh
ringfour-cli app settings show <installation-id> --json
ringfour-cli app settings set <installation-id> --file live-settings.json --json
ringfour-cli app artifacts --app <app-id> --org <workspace-id> --json
ringfour-cli app artifacts --app <app-id> --robot <robot-name> --path-prefix reports/
ringfour-cli app artifact <run-id> <artifact-id> --output ./downloaded-summary.json
```

Confirm `settings set` reports `saved_for_next_start` for an idle installation
and `pending` with its application/run IDs for an active one. Verify the
rejection and stale-selection errors, and confirm the downloaded artifact is
not overwritten if the destination already exists. An unresolved `pending`
result is not an applied success.

## Recovery scenarios

Perform these only on the disposable acceptance workspace and after recording
the exact App run/application IDs:

1. Interrupt API connectivity after the Daemon durably records an App result.
   Restore connectivity and confirm the same result reaches Logbook once.
2. Interrupt the App acknowledgement after the handler applies values. Replace
   the Daemon using the operator's ordinary recovery procedure. Confirm the
   same application ID is retried, the container is not relaunched, and a later
   run receives no old request.
3. Stop a run with settings pending, start a new run, and confirm old results
   do not alter the new run or overwrite a newer selected revision.
4. Disconnect a robot and confirm Studio shows last-observed state and time,
   preserving the previous applied values as confirmed history.

Record both user identities, workspace IDs, App release/digest, robot IDs,
installation IDs, run/application/operation IDs, observed outputs, and exact
commands in `docs/evidence/AP-17.md`. Redact tokens and credentials. Keep AP13
acceptance separate.
