# Combined App acceptance after AP-14/AP-15 reduction

Run this once with cdr (main account) and ring1 (Outlook account), after the operator reloads Platform and the virtual device stack. This sweep covers the remaining human checks for Apps, runtime, virtual deployment, Console/CLI parity, settings and lifecycle responsiveness. Individual AP guides remain references for detailed negative cases; this is the execution order and record of the combined pass.

## 1. Operator reload and identity preservation

From the Platform checkout:

```sh
./up.sh -d --build
```

This builds/recreates the Platform services and applies pending EF migrations through normal API startup. Users, organizations and memberships stay. AP-14/AP-15 deliberately drop old mission/script/dev-session/UI state.

From the virtual checkout, keep the same project name, instance numbering and environment as your running robot:

```sh
RINGFOUR_ALLOW_DIRTY_APP_SOURCES=true ./up.sh -d
# For existing numbered instances, instead use the existing instance count:
RINGFOUR_ALLOW_DIRTY_APP_SOURCES=true ./upn.sh 2
```

Use the dirty-source opt-in only for this reviewed local working tree. Existing --apps launcher arguments remain accepted. compose.yaml now contains only Agent and daemon; the obsolete Runner service is removed by --remove-orphans. Enrollment/data volumes remain.

Check API health and each daemon's health/status ports. Daemon readiness must report sqlite and engine, never Runner. Confirm your existing robot UUID and App bindings remain. Do not use down -v for this acceptance.

In each user's existing authenticated shell, from Platform:

```sh
uv run --project apps/cli ringfour-cli whoami
uv run --project apps/cli ringfour-cli org list
uv run --project apps/cli ringfour-cli --help
uv run --project apps/cli ringfour-cli app --help
```

Pass: both accounts retain their identities/memberships. Help includes App operations and has no mission/dev/execution/legacy artifact groups, top-level script run/deploy/logs, or robot fixture commands. ring1 continues using its own config and credential store.

## 2. Publish and consume one release

As cdr, select the publisher organization, then use a new temporary authoring directory:

```sh
uv run --project apps/cli ringfour-cli org select PUBLISHER_ORG_UUID
uv run --project apps/cli ringfour-cli app init /tmp/ap15-robot-check \
  --app-key ap15-robot-check --repository 127.0.0.1:5000/ringfour/ap15-robot-check
uv run --project apps/cli ringfour-cli app validate /tmp/ap15-robot-check --json
uv run --project apps/cli ringfour-cli app build /tmp/ap15-robot-check --json
uv run --project apps/cli ringfour-cli app publish /tmp/ap15-robot-check --json
```

Record App ID, revision ID and immutable image digest. Repeat publish: the same frozen request must replay without creating a conflicting release.

As ring1, select the consumer organization:

```sh
uv run --project apps/cli ringfour-cli org select CONSUMER_ORG_UUID
uv run --project apps/cli ringfour-cli app search ap15-robot-check
uv run --project apps/cli ringfour-cli app import REVISION_UUID --json
uv run --project apps/cli ringfour-cli robot list
uv run --project apps/cli ringfour-cli app install REVISION_UUID --robot ROBOT_UUID --json
uv run --project apps/cli ringfour-cli app operation OPERATION_UUID --wait
```

Pass: listed release is discoverable and imported into the consumer workspace. Installation reaches applied state without starting a run. Studio shows the same installation/revision/configuration. If using two robots, repeat install on robot 2 and verify their bindings stay independent.

## 3. Run, configure, inspect, repeat

Use the App page in Studio or CLI:

```sh
uv run --project apps/cli ringfour-cli app start INSTALLATION_UUID --json
uv run --project apps/cli ringfour-cli app run RUN_UUID
uv run --project apps/cli ringfour-cli app logs RUN_UUID --follow
uv run --project apps/cli ringfour-cli app logbook --run RUN_UUID
```

Pass: real Agent IMU output arrives, run ends once, and Home/robot/App/activity views agree on the exact run ID and terminal state. Tabs retain content and update without flashing the entire view. Observe action-to-visible-state timing, especially start, stop and terminal refresh.

Change sample_count through Studio configuration, rerun, and count samples. Existing run snapshots/history must remain immutable. Test update to another release and rollback to the earlier binding; a failed preparation must retain the prior installed binding. A second start while the robot is occupied must be rejected rather than launch overlapping work.

## 4. Continuous photo App and stop

Use the existing stationary photo example already published in your environment. Keep its 30-second interval; no motion is required. Start it, wait for at least two images, and stop the exact run through Studio or:

```sh
uv run --project apps/cli ringfour-cli app stop INSTALLATION_UUID --run RUN_UUID --json
uv run --project apps/cli ringfour-cli app operation OPERATION_UUID --wait
uv run --project apps/cli ringfour-cli app artifacts RUN_UUID
uv run --project apps/cli ringfour-cli app artifact RUN_UUID ARTIFACT_UUID --output /tmp/ap15-photo.jpg
```

Pass: files appear while running, download correctly and remain after stop. No new photos appear after terminal stop. Logbook and the main App view agree. App-wide files preserve run/robot attribution across multiple runs and both robots.
