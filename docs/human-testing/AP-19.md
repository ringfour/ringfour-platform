# AP-19 human acceptance — responsive App state

This guide measures one complete App lifecycle and checks that the Home,
Robots, Apps, App Overview, Activity and Logbook views agree. Run against a
disposable test organization/robot where possible. Use the existing
Camera Snapshot Loop or another harmless App; do not use a motion-capable
release for this acceptance.

## Prerequisites

- Platform API/PostgreSQL, Console, Daemon and a camera-capable test robot are
  healthy. Record exact versions/image digests and whether requests are local
  or cross-host.
- Browser developer tools can record a Performance profile and Network HAR.
  API and PostgreSQL logs/metrics are available with secrets redacted.
- A publisher and operator account can access the same intended workspace.
- Do not restart or rebuild either stack as part of this guide. If the tested
  code requires a stack reload, stop and ask the operator to run it.

## 1. Capture a baseline

1. Open Home with Network “Preserve log” enabled. Record navigation start,
   first useful content, settled view, request count, transferred bytes, and
   each request's wait/server/download timing. Repeat warm and after a hard
   reload.
2. Repeat on Apps and Robot detail. Note whether a refresh replaces the list
   or detail with a loading placeholder, whether scrolling/selection resets,
   and how many requests scale with historical runs, Apps, installations and
   robots.
3. Start one harmless App. Record action time, API request/response, operation
   ID, run ID, Daemon receipt, engine start, device report receipt, each view's
   first visible accepted/running state, and final terminal state. Use the same
   run ID throughout; the reported discrepancy to investigate is
   `66ac710b-cec1-460d-91be-8675436c9d98`.
4. Correlate API spans with Postgres query duration/lock wait and Daemon
   WebSocket/reconciliation/outbox timestamps. Do not include access tokens,
   device secrets, full container environment or private image credentials in
   exported evidence.

## 2. Verify exact run-state agreement

1. In Logbook, open the App event and copy its `run_id`. Compare it with the
   run detail API, workspace run list, installation overview and Home row.
2. Confirm every view links to the same run record and displays its actual
   state. An `app.run.started` event is history and must not independently
   prove that the run is still active.
3. While the device is disconnected, confirm the UI indicates last observed
   state and observation time rather than presenting stale state as current.
   Reconnect and verify the matching run transitions without creating a
   duplicate run or changing its ID.
4. Start and stop a second run in sequence. Delayed refreshes from the first
   must not replace the newer run or cause Stop to target it. Stop must remain
   scoped to the exact active run.

## 3. Verify refresh behavior and request scaling

1. Keep the Apps list open while a background update arrives. Content remains
   mounted; changed status appears in place, with no full-page/list flicker,
   scroll reset or lost robot selection. A small busy indicator is acceptable.
2. Trigger a manual refresh and a start/stop action. The view refreshes
   promptly, but does not blank. Delay an older response in browser tools if
   feasible; it must not overwrite a newer response. Multiple timers or rapid
   refreshes must not create overlapping request storms.
3. Check that initial Home and Apps views request bounded current/recent data.
   Adding historical runs must not add one request per run; adding robots or
   installations must not produce an unbounded detail-request waterfall.
   Historical pages remain available by cursor when explicitly requested.
4. Verify workspace switching clears or replaces prior workspace data and
   that each projection/history endpoint still enforces the caller's
   organization and robot access.

## 4. Verify metadata and digest identity

1. Publish a listed release with a display name change but unchanged App
   source/image bytes. Confirm the OCI image digest stays the same and the
   canonical manifest/release digest changes.
2. Confirm the Store and imported App display the new listed name consistently;
   running/history snapshots keep their original release and image identity.
3. Retry the exact same App key, release and manifest and confirm it is
   idempotent. Attempt the same key/release with changed metadata/content and
   confirm a clear conflict with no partial catalog rename or misleading
   image-cache result.
4. Change source bytes and publish a new release. Confirm the image digest
   changes when the built image changes, and that older run details still
   resolve to the original immutable digest.

## Acceptance targets

For a warm local healthy stack, measure action-to-visible-state separately
from requested-to-device-observed state:

- Start/stop accepted state appears at p95 ≤ 1 second.
- Device-observed transition appears at p95 ≤ 1.5 seconds.
- Home and Apps useful first render p95 ≤ 1.5 seconds with 10 robots and 100
  Apps in the agreed fixture.
- Request count does not grow with historical run count; no whole-view flicker
  occurs on background/manual refresh.

If a target fails, report the slowest measured segment and its evidence rather
than attributing the total to PostgreSQL by assumption. Save sanitized HAR,
timing table, query plans, run IDs and exact software pins in
[`AP-19 evidence`](../evidence/AP-19.md).
