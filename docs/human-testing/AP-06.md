## 2. Initialize and validate

From Platform use the updated CLI directly, preserving the existing login and
workspace settings:

```sh
uv run --project apps/cli ringfour-cli app init /tmp/my-check \
  --app-key my-check --repository registry.example.com/team/my-check --json
uv run --project apps/cli ringfour-cli app validate /tmp/my-check --json
```

Replace the example repository with your operator-allowed OCI registry/repository.
The destination must not exist, even as an empty directory. `--template-archive`
can point to a transferred archive; its bytes must match the packaged pin.
Identity is selected by the caller. No robot or workspace selection is copied.

`app.json` contains editable target repositories, metadata, capability requirements,
configuration schema/defaults, explicit source files and the AP-04 wheel bundle
pin. It is not accepted by the publication API. Configuration is one integer:
`sample_count`, 1–20, default 1. Boolean, out-of-range and extra values fail.
The manifest fixture uses that existing field; no interval field is introduced.

Validation is offline and needs no login. Try invalid default count 0, duplicate
targets, an unsupported architecture or undeclared config key; expect a structured
error and nonzero exit. Restore the valid document afterward. Source file paths
must be relative regular files; traversal, symlinks, environment files and
credential/context/state files are refused. Unlisted extra files are not staged.

## 3. Build with local wheels

```sh
uv run --project apps/cli ringfour-cli app build /tmp/my-check \
  --wheels /home/cdr/.local/share/ringfour/python-artifacts/0.1.0.dev0 --json
```

Buildx and a Linux Docker engine are required. Publication's platform-specific
push requires Engine API >=1.46. The build reads only declared sources and
checksum-verified wheel inputs; no sibling code or Runner wheelhouse is used.
The default template pins Python/uv images and all Python dependency wheels.
The App has one plain entrypoint, runs as uid 10001 and receives no engine socket.

`.ringfour/build.json` records source fingerprint, exact local image ID and
platform. Editing sources after build, replacing a local image tag or changing
wheel bytes prevents publication. No image is started by build/publish.

## 4. Publish, retry and release a new revision

Use Docker's normal `docker login` for your registry and the existing Auth0 CLI
login/workspace selection. Configure AP-05 server registry policy first; private
repository policies must bind to your publisher workspace. Then:

```sh
uv run --project apps/cli ringfour-cli app publish /tmp/my-check --visibility listed --json
```

Images are pushed and checked as concrete manifest/config platform targets.
The CLI freezes `.ringfour/releases/0.1.0.json` and writes final
`app.manifest.json` before posting metadata to AP-05. Expect 201-equivalent
CLI success with server App/revision IDs, publisher and manifest digest.
Registry success followed by API failure leaves a retryable frozen request.
Retry using the same workspace/visibility/API selection. Default idempotency
keys are deterministic for those settings and exact request; `--idempotency-key`
is available for callers managing their own key. A frozen retry does not repush
or require the registry online before the server can replay its committed result.

After publication, the App is discoverable through AP-05 Store reads. This does
not create an installation or run. Store import/installation/run UI and operator
commands arrive in later milestones; the [example README](../../../robot-check/README.md)
describes that intended flow without claiming those commands already ship.

To change source/configuration/dependencies, bump `release` in `app.json` before
building/publishing again. Rebuilding or modifying a frozen release is refused;
v1's snapshot and hosted metadata remain unchanged when v2 is published.

For independently prepared images:

```sh
uv run --project apps/cli ringfour-cli app validate --manifest /path/to/app.manifest.json --json
uv run --project apps/cli ringfour-cli app publish --manifest /path/to/app.manifest.json --json
```

Tags and indexes are refused in final manifests. Remote digest/platform mismatch
or verification failure prevents metadata publication. Use `app --help` and each
nested `--help`; legacy mission commands remain until AP-15.

## 5. Verify robot behavior when the simulator is available

Robot Check reads only the verified SDK's `robot.imu()` through NET. A first
baseline stamp must advance before it emits a sample. Output includes UTC
observation time, Agent sample stamp/frame and acceleration. Set
`RINGFOUR_AGENT_URL` to the integrator's reachable Agent on its private network
and optionally `RINGFOUR_APP_CONFIG` to an owner-provided JSON file. Compare
counts 1 and 2; expect exactly that many `robot_check.imu` records followed by
`robot_check.complete`. SIGTERM/SIGINT ends sampling with `robot_check.stopped`.

The image can run standalone under operator control; it is not a Ringfour App
run until AP-08/09 supplies device execution. Runtime credentials are not
fabricated for this check. When a proper runtime is configured, the optional
client writes `Robot Check IMU sample`; App runtime credential/delivery support
is AP-10. Unconfigured standalone use writes stdout only.

In this session the deployed Agent was reachable but sampling timed out, and no
Base101 simulator container was running. No live IMU success is claimed. Start
the simulator through its normal operator workflow before this check. No stack
operation was performed by the agent.
