performed by the operator. The currently enrolled `virt2` needs no recovery or
reload to complete AP-03.

## 2. Recover old virtual enrollment once after the AP-02 reset

Skip this step for the valid current `virt2` enrollment or a new/unpaired
Daemon. Use it only for a stale enrollment left over from AP-02. The Platform
reset removed robot records/credentials while the old Daemon kept its identity.
With virtual stopped, archive its DB and credentials together before pairing
again. This
operator recovery action keeps the old outbox offline:

```bash
cd /home/cdr/ringfour/ringfour-virtual
docker compose -f compose.yaml run --rm --no-deps --user 0 --entrypoint /bin/sh daemon -c '
set -eu
archive="/data/pre-apps-$(date -u +%Y%m%dT%H%M%SZ)"
mkdir -m 700 "$archive"
for name in ringfour.db ringfour.db-wal ringfour.db-shm robot-credential pairing-pending.json; do
  if [ -e "/data/$name" ]; then mv "/data/$name" "$archive/"; fi
done
'
```

Do not run while Daemon is running. DB and credential represent one enrollment;
archive them together. Existing Runner data remains for its legacy recovery
gates. This inventory check starts no robot work.

## 3. Reload virtual services and pair

Start Base101 using its normal workflow if the simulator is not running, then:

```bash
cd /home/cdr/ringfour/ringfour-virtual
RINGFOUR_STATUS_HOST_PORT=8085 ./up.sh -d
```

Port 8085 is a device-status override; Adminer now uses 9080. The launchers read the deployment engine
OS/architecture with `docker info`; Daemon receives the instance-specific Agent
URI. No Docker socket is mounted for this milestone. Direct Compose starts
must explicitly supply `RINGFOUR_ENGINE_OS`/`RINGFOUR_ENGINE_ARCHITECTURE` or
reporting stays disabled.

Open `http://localhost:8085`, obtain the new pairing code and claim it through
Console as an owner using the normal pairing flow. Do not send codes or
credential secrets in chat. Allow one report interval (15 seconds) plus the
device connection enrollment polling interval.

## 4. Inspect the report

In Adminer, inspect `robot_app_inventory` for the newly enrolled robot:

- Namespace UUID is stable and distinct from profile name `base101`.
- Supported is true, sequence is positive and receipt time is recent.
- Platform matches the real Docker engine (x86_64/aarch64 normalized).
- Source is `agent_welcome`, protocol 1, with profile name/model/version.
- Base101 advertises mobility, cameras, lidar, imu, slam, teleop, watches,
  places, audit and status, with `cameras: [base]`.

Members can read the same data at `GET /v1/robots/{robot_id}/app-status` using
their Auth0 access token. Current connectivity/support are separate from the
last report and its original timestamps. Unknown well-formed advertised IDs
remain explanatory; they do not become authoring predicates automatically.

`GET /v1/robots/{robot_id}/app-compatibility?revision_id=...` previews a stored
revision the caller may access. Publishing is AP-05, so do not fabricate
releases in the live DB for this check. Isolated tests cover these previews and
their authorization/refusals. Later install/start paths consume the fresh gate.

## 5. Restart and unavailable checks (operator actions)

Record a report sequence and namespace, restart Daemon through the normal
operator workflow, and verify the same namespace with advancing sequence.
Stop Agent temporarily: after a bounded read, inventory becomes unavailable,
reason `agent_unreachable`, retaining `last_successful`. Restart Agent to
restore current inventory. Disconnect Daemon: status becomes offline and
retains original observation/receipt times. Reconnect negotiates a new session.
Advertising IMU does not prove a live reading or motion permission.

Ringfour stack. Repeat it with:
