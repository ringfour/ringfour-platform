# Human testing — milestone 09

The existing live Platform and `ringfour-virtual` stacks have passed no-motion
checks for pending wait, daemon restart recovery, response application, timeout,
late-response rejection, cancellation races and sequential execution binding.
The Console participated in a live pending/submitted/confirmed flow, but exact
browser refresh/retry presentation and multi-user acceptance remain open. See
[live evidence](../evidence/09.md).

## Prerequisites

- build and install the current `ringfour-platform-runtime` wheel in a mission;
- rebuild/reload the ringfour-virtual stack so Runner and daemon contain the new
  endpoint and migration;
- rebuild/reload the Platform stack so its PostgreSQL migration and API endpoint
  are active;
- use a mission execution with a stable UUID request ID.

Do not use a timeout choice that can initiate motion or another unsafe action
without approval.

## Pending request and optional timeout

In mission code, call `interactions.create` using the default example in
`packages/python-runtime/README.md`, without a deadline. Call
`interactions.wait`; it should remain blocked while the interaction is pending.
Submit a human response and confirm the mission resumes exactly once. For the
separate timeout branch, create a new interaction with an explicit deadline
around 30 seconds ahead and a safe `timeout_outcome`; pass `on_timeout` to
`interactions.wait` and confirm it runs once after daemon timeout confirmation.

Expected result: creation returns only after the daemon has stored the request.
Without a configured deadline, no response means the mission stays pending and
does not choose an outcome. With an explicit deadline, the daemon reaches
`timed_out`, the outcome equals the configured safe choice, and `on_timeout`
runs once in mission code. Restarting the daemon while pending must preserve
the interaction.

## Replay and conflict

Create the same request ID and exact payload twice during one running execution.
Expected result: both calls return the same interaction. Reuse the ID with a
different prompt or choices. Expected result: the runtime rejects it with HTTP
409 and the original row remains unchanged.

## Execution binding and stop

Attempt to read a request using another execution's credential. Expected result:
it is inaccessible. Stop the owning mission while its interaction is pending.
Expected result: a subsequent daemon reconciliation/read reports `cancelled`;
it must never report approval. A Runner outage alone must not fabricate
cancellation or approval. Restart the daemon while the mission is waiting: the
SDK should retry the transient local connection failure, the request should
remain pending, and the mission should resume waiting after the daemon reconnects.

## Operator response

With an interaction pending, list and inspect it:

```sh
ringfour-cli hitl list
ringfour-cli hitl show REQUEST_ID
```

Submit one of its exact choice values:

```sh
ringfour-cli hitl respond REQUEST_ID continue --idempotency-key demo-answer-1
```

Expected result: the first command response says `submitted` and warns that the
daemon has not yet confirmed it. Re-run `hitl show`; after device sync it must
show interaction state `answered`, the chosen outcome, response status
`applied`, and the operator user ID. Repeating the same key and value returns
the same response ID. A different key or competing operator gets a conflict.
In Logbook for the same execution, confirm `Human input requested` is attributed
to the execution initiator and `Human interaction answered` is attributed to
the responding operator, with the selected label/value visible. A provisional
response must not create an applied-answer entry.

Repeat while the robot is offline. The API may show `submitted`, but must not
show `answered`. After the local deadline and reconnection, the daemon reports
`timed_out`, the safe timeout outcome wins, and the response becomes
`rejected_timed_out`. An operator from another organization must receive 404.

## Console Overview

Open the Console Overview for the interaction's workspace. Expected result: a
pending request appears above the workspace metrics with its robot, deadline
or “No timeout”,
prompt and exact finite choices. Choose a response. The buttons become disabled
and the request says it is waiting for device confirmation. It must remain in
the queue while the robot is offline and disappear only after daemon-confirmed
answer, timeout or cancellation. Refresh the page after a lost response; retry
must not create a second answer.

Record exact commands, versions and observed output in `docs/evidence/09.md`.
Milestone 09 remains incomplete until the outstanding concurrent execution,
multi-operator, cross-workspace and full Console acceptance gates are closed.
