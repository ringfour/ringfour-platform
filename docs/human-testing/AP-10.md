# AP-10 — App runtime and durable evidence

Use the [combined AP-08/09/10 human pass](AP-08-10.md). This is additional operator
confidence after automated component and actual-protocol acceptance. Human checks
do not block the authorized implementation sequence.

Deploy the updated API (AppRuntimeEvidence after AppRunDispatch) and Daemon
(SQLite 0020 after 0019), preserving their data. Use the AP-07 operator overlay.
It sets RINGFOUR_APP_RUNTIME_URL to the owner-controlled Daemon alias on the App
network. This origin must be reachable from an App. Only Daemon has the engine
socket. App mounts contain its own artifact volume, never daemon-data.

The SDK and optional runtime are separate pinned wheels. Runtime clients retain
logbook.info(), artifacts.publish_file(), interactions.create/get/wait(). The
App receives run-scoped URLs/tokens and RINGFOUR_ARTIFACT_DIR automatically.
A private persisted Daemon key derives recoverable tokens; SQLite stores hashes,
expiry and revocation only. Credentials are independent of Runner. They are
rejected once the run is terminal. Treat the engine administrator as trusted.

## Prepare the runtime test App

Use a new temporary authoring directory and one test release; this is a lifecycle
fixture, not another default product example. Keep Robot Check for real IMU proof.

```sh
cd /home/cdr/ringfour/ringfour-platform
uv run --project apps/cli ringfour-cli app init /tmp/runtime-acceptance \
  --app-key runtime-acceptance --repository 127.0.0.1:5000/ringfour/runtime-acceptance
cp tests/fixtures/apps/runtime/main.py /tmp/runtime-acceptance/main.py
uv run --project apps/cli ringfour-cli app validate /tmp/runtime-acceptance --json
uv run --project apps/cli ringfour-cli app build /tmp/runtime-acceptance --json
uv run --project apps/cli ringfour-cli app publish /tmp/runtime-acceptance --json
```

Install the returned revision on virt2 through AP-07 and start its installed
binding through AP-09. The program uses the pinned runtime wheel: it publishes
proof.bin, changes/deletes its source, writes an authored Logbook entry referencing
that artifact, then waits for a human choice. Stdout contains runtime.ready with
request_id and artifact_id. No Runner call supplies these services.

## Inspect and answer

Set API, TOKEN, ORG and RUN using your existing Auth0/CLI workspace. Use Operator,
Developer or Owner membership. Keep tokens private. Set REQUEST and ARTIFACT from
runtime.ready (see stdout below).

- GET /v1/app-runs/$RUN/output?stream=stdout returns bounded base64 bytes,
  offset/next_offset, sealed and truncated. Decode data_base64; offsets count
  bytes, including Unicode. stderr has an independent cursor.
- GET /v1/app-runs/$RUN/artifacts lists uploaded artifacts. GET
  /v1/app-runs/$RUN/artifacts/$ARTIFACT/content must return exactly
  `original immutable evidence`, even though the App deleted the source.
- GET /v1/organizations/$ORG/app-logbook?run_id=$RUN shows the authored entry,
  start and pending interaction. With installation_id or app_id instead, the
  same event IDs and exact run attribution must appear.

```sh
curl --fail-with-body -sS "$API/v1/app-runs/$RUN/interactions/$REQUEST" \
  -H "Authorization: Bearer $TOKEN"
curl --fail-with-body -sS "$API/v1/app-runs/$RUN/interactions/$REQUEST/responses" \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -H 'Idempotency-Key: runtime-acceptance-answer-1' --data '{"chosen_value":"yes"}'
```

The response initially says submitted. Poll until response.status is applied;
the Daemon confirms application. The App prints runtime.answered with yes and
exits successfully. Output becomes sealed after final collection/delivery. Run,
artifacts, authored evidence and decision remain readable after completion.

## Recovery and negative checks

Use a fresh run/key for each scenario. Operator performs all stack interruptions.

- Replace only Daemon while the App waits, retaining daemon-data. Container ID
  and StartedAt remain identical. Submit the choice while Daemon is stopped:
  it stays submitted; after replacement it becomes applied exactly once.
- Interrupt API connectivity after local artifact publication. Delete/modify the
  source (the fixture already does this), replace Daemon, then restore API.
  Original bytes and authored evidence arrive from its private durable spool.
- Stop while waiting. The request becomes cancelled; an outstanding provisional
  answer cannot become applied afterward. Engine outage alone must not cancel it.
- Try another run's interaction path or artifact ID: 404. A separate workspace
  cannot read bytes or answer. A competing second answer returns a distinct
  conflict; identical idempotent replay returns the winning response.
- The existing runtime clients support finite deadlines and timeout outcomes as
  well as indefinite prompts. Confirm timed_out is distinct from stop cancellation
  and that late answers are rejected. No implicit approval on timeout/disconnect.

Spools are private under the Daemon data directory. Acknowledged artifact byte
files are removed only after hosted confirmation; metadata remains for replay.
Per-run artifact engine volumes are retained for operator-managed retention;
there is no automatic prune. Existing legacy Logbook/HITL/byte routes continue
for legacy clients; App history uses the new workspace app-logbook route.
